# v1 版本服务端架构

## 1. 文档定位

本文总结 v1 版本服务端的实际实现，作为当前代码的架构基线。

v1 目标是完成在线即时通信闭环：

- 邮箱验证码。
- 用户注册、登录和重置密码。
- ChatServer 动态分配。
- TCP 长连接认证。
- 用户搜索。
- 好友申请和好友认证。
- 双 ChatServer 在线文本消息转发。

v1 不包含：

- 离线消息。
- 聊天历史持久化。
- 心跳和自动重连。
- 踢人。
- 同账号在线互斥。
- 群聊。

## 2. 技术栈

| 模块 | 技术 |
| --- | --- |
| GateServer | C++17、Boost.Beast HTTP、Boost.Asio |

## 4. GateServer

GateServer 是对外 HTTP 入口，负责认证相关请求。

### 4.1 主要类

| 类 | 职责 |
| --- | --- |
| `CServer` | 监听 HTTP 端口并接受连接 |
| `HttpConnection` | Beast HTTP 请求读取与响应写回 |
| `LogicSystem` | HTTP 路由与业务处理 |
| `VerifyGrpcClient` | 调用验证码服务 |
| `StatusGrpcClient` | 分配 ChatServer 并获取 Token |
| `MysqlDao/MysqlMgr` | 用户、密码和邮箱数据访问 |
| `RedisMgr` | 验证码读取 |
| `PasswordHasher` | Argon2id 哈希与校验 |

### 4.2 HTTP 接口

| 路径 | 作用 |
| --- | --- |
| `POST /get_verifycode` | 请求邮箱验证码 |
| `POST /user_register` | 用户注册 |
| `POST /reset_pwd` | 重置密码 |
| `POST /user_login` | 密码登录并分配 ChatServer |
| `GET /get_test` | 开发测试接口 |

### 4.3 注册

```text
客户端提交 email/user/passwd/confirm/verifycode
  → 检查密码与确认密码
  → 从 Redis 读取 code_<email>
  → PasswordHasher::Hash
  → MySQL reg_user 存储过程
  → 返回 uid/email/user
```

密码只保存 Argon2id 字符串，不保存原始密码或 XOR 结果。

### 4.4 登录

```text
客户端提交 email/passwd
  → MySQL 根据邮箱读取 password_hash
  → PasswordHasher::Verify
  → StatusServer.GetChatServer
  → 返回 uid/token/host/port
```

Token 由 StatusServer 生成并写入 Redis，TTL 默认 30 分钟。

### 4.5 成功回包

业务成功状态设置在主要操作完成之后：

- 注册：数据库插入成功。
- 重置密码：数据库更新影响至少一行。
- 登录：密码校验和 ChatServer 分配成功。
- 验证码：VerifyServer 调用成功。

## 5. VerifyServer

VerifyServer 使用 Node.js 实现验证码 gRPC 服务。

### 5.1 流程

```text
GateServer 请求验证码
  → 查询 Redis code_<email>
  → 已存在则复用
  → 不存在则生成 4 位验证码并写入 Redis
  → nodemailer 发送邮件
```

验证码 Redis TTL 为 600 秒。

v1 直接复用现有验证码进行重发，不记录验证码原文日志。

### 5.2 gRPC

```proto
service VerifyService {
  rpc GetVerifyCode(GetVerifyReq) returns (GetVerifyRsp);
}
```

## 6. StatusServer

StatusServer 负责 Token 签发和 ChatServer 分配。

### 6.1 GetChatServer

```text
读取 Redis logincount Hash
  → 选择当前在线计数最小的 ChatServer
  → 生成随机 Token
  → SET utoken_<uid> <token> EX <ttl>
  → 返回 host/port/token
```

默认 TTL：

```ini
[Auth]
TokenTtlSeconds = 1800
```

Token 写入失败时不会返回成功。

### 6.2 Login

兼容用接口：

```text
Get utoken_<uid>
  → 与请求 Token 比较
  → 返回认证结果
```

当前 GateServer 登录主流程直接使用 `GetChatServer`，ChatServer TCP 登录也直接校验 Redis Token。

## 7. ChatServer

ChatServer1 和 ChatServer2 使用相同代码，仅配置不同。

### 7.1 启动流程

```text
读取 config.ini
  → 初始化 AsioIOServicePool
  → logincount.<SelfServer.Name> = 0
  → 启动 gRPC Server
  → 启动 TCP CServer
```

### 7.2 线程模型

ChatServer 主要有四条执行路径：

1. Boost.Asio IO 线程处理 TCP 连接。
2. `LogicSystem` 单工作线程串行处理业务消息。
3. `CSession` 异步写回并使用发送队列。
4. gRPC Server 线程处理跨节点通知。

`CSession` 负责：

- 4 字节 TCP 帧头。
- 半包和粘包处理。
- 最大消息体 2048 字节校验。
- 异步读取和发送队列。

### 7.3 业务分发

`LogicSystem::RegisterCallBacks` 只注册五条映射：

```text
1005 → HandleChatLogin
1007 → HandleSearchUser
1009 → HandleAddFriend
1013 → HandleAuthFriend
1017 → HandleTextChatMsg
```

五个处理器均定义在 `LogicSystem.cpp`，`DealMsg` 统一处理队列和异常边界。

### 7.4 TCP 帧

```text
2 字节消息 ID（大端）
2 字节消息体长度（大端）
N 字节 JSON 消息体
```

约束：

```text
N <= 2048
```

### 7.5 TCP 消息

| ID | 方向 | 作用 |
| --- | --- | --- |
| 1005 / 1006 | 客户端 ↔ Chat | TCP 登录 |
| 1007 / 1008 | 客户端 ↔ Chat | 用户搜索 |
| 1009 / 1010 | 客户端 ↔ Chat | 好友申请 |
| 1011 | Chat → 客户端 | 被申请通知 |
| 1013 / 1014 | 客户端 ↔ Chat | 好友认证 |
| 1015 | Chat → 客户端 | 被认证通知 |
| 1017 / 1018 | 客户端 ↔ Chat | 文本消息 |
| 1019 | Chat → 客户端 | 文本消息通知 |

### 7.6 Session 身份

TCP 登录成功后：

```cpp
sess->SetUserId(uid);
UserMgr::GetInst()->SetUserSession(uid, sess);
```

好友申请、好友认证和聊天中的当前用户身份统一使用：

```cpp
sess->GetUserId()
```

请求体中的操作者身份不再作为可信来源。

### 7.7 在线计数

登录成功：

```text
HINCRBY logincount <server_name> 1
```

断线清理：

```text
HINCRBY logincount <server_name> -1
```

每次进程启动都会把本节点计数重置为 0，避免崩溃后的旧值残留。

## 8. 好友关系

### 8.1 申请和认证

```text
A 申请 B
  → INSERT friend_apply(A,B,status=0)
  → 通知 B

B 同意 A
  → 事务更新 friend_apply(A,B,status=1)
  → 插入 friend(B,A)
  → 插入 friend(A,B)
```

### 8.2 聊天授权

文本消息发送前调用：

```cpp
MysqlMgr::GetInst()->AreFriends(uid, to_uid);
```

查询要求双向记录都存在。

### 8.3 好友列表

好友列表使用一次 JOIN：

```sql
SELECT
    u.uid, u.name, u.email, u.nick, u.`desc`,
    u.sex, u.icon, f.back
FROM friend f
JOIN user u ON u.uid = f.friend_id
WHERE f.self_id = ?
ORDER BY f.id ASC;
```

避免对每个好友重复查询用户表。

## 9. 文本消息

### 9.1 同节点

```text
A 1017
  → Session 身份校验
  → AreFriends
  → 从 UserMgr 查找 B Session
  → B 收到 1019
  → A 收到 1018
```

### 9.2 跨节点

```text
A 1017
  → 查询 Redis uip_<B>
  → gRPC NotifyTextChatMsg
  → B 所在 ChatServer
  → B 收到 1019
  → A 收到 1018
```

文本唯一标识使用客户端生成的字符串：

```text
unique_id
```

## 10. MySQL

主要表：

| 表 | 作用 |
| --- | --- |
| `user` | 用户资料和密码哈希 |
| `user_id` | 用户 UID 序列 |
| `friend_apply` | 好友申请与状态 |
| `friend` | 双向好友关系与备注 |

关键索引：

```text
user: PRIMARY(id), UNIQUE(uid), UNIQUE(name), UNIQUE(email)
friend_apply: UNIQUE(from_uid,to_uid), INDEX(to_uid,status,id)
friend: UNIQUE(self_id,friend_id), INDEX(friend_id,self_id)
```

数据库初始化：

```text
server/sql/schema.sql
```

已有库迁移：

```text
server/sql/migrations/001_password_hash.sql
server/sql/migrations/002_database_cache_indexes.sql
```

## 11. Redis

| Key | 类型 | 内容 | TTL |
| --- | --- | --- | --- |
| `code_<email>` | String | 邮箱验证码 | 600 秒 |
| `utoken_<uid>` | String | 登录 Token | 默认 1800 秒 |
| `uip_<uid>` | String | 用户所在 ChatServer | 当前无 TTL |
| `ubaseinfo_<uid>` | String | 用户公开资料 JSON | 默认 600 秒 |
| `nameinfo_<name>` | String | 用户名对应 UID | 默认 600 秒 |
| `logincount` | Hash | 各 ChatServer 在线连接数 | 当前无 TTL |

`ubaseinfo_<uid>` 是唯一完整资料缓存，`nameinfo_<name>` 只保存 UID，避免同一资料保存两份。

## 12. 认证与安全

v1 已采用：

- Argon2id 密码哈希。
- 密码哈希不进入 ChatServer 和 Redis 用户资料缓存。
- Session UID 作为好友与聊天操作的可信身份。
- 聊天双方必须为好友。
- Token 带 TTL。
- 业务成功回包在主要操作完成后设置。
- 配置文件通过 `config.example` 提供模板，真实本地配置不进入版本库。

## 13. 构建与验证

服务端构建：

```powershell
cmake --preset windows-vcpkg
cmake --build build --config Debug --target GateServer StatusServer ChatServer ChatServer2
```

端到端测试：

```powershell
node server\tests\p0_security_smoke.js
```

测试覆盖：

- Argon2id 注册和登录。
- Token TTL。
- 在线计数原子增减。
- 未登录访问拒绝。
- 好友申请和认证。
- 陌生人聊天拒绝。
- 好友文本消息投递。
- 伪造发送者拒绝。
- 用户资料缓存模型和 TTL。

## 14. 已知限制

- 同一账号重复登录仍可能覆盖 UID → Session 映射。
- 未实现踢人。
- 未实现心跳和断线重连。
- HTTP 未启用 HTTPS。
- 内部 gRPC 使用明文连接，未启用 mTLS。
- 文本消息只在线转发，不保存聊天记录。
- 离线消息未实现。
- 好友列表暂未分页。
- ChatServer 和 ChatServer2 仍保留大量重复源码。
- 未接入统一结构化日志、指标和链路追踪。

## 15. v1 结论

v1 已经具备完整的在线聊天主链路和双 ChatServer 转发能力，认证、身份可信、好友授权、在线状态和数据缓存均达到可演示、可继续演进的状态。

下一版本应优先处理同一账号在线策略、踢人、心跳和重连，再考虑 ChatServer 合并、传输加密与可观测性。
