# v1 版本服务端架构

## 0. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 |
| 基准日期 | 2026-10-23 |
| 代码分支 | `feature/迭代优化` |
| 架构类型 | HTTP 网关 + gRPC 服务协作 + 双 TCP 聊天节点 |
| 主要语言 | C++17、Node.js |
| 数据存储 | MySQL 8、Redis |

本文是当前 v1 服务端代码的架构基线。历史文档中的 3.0/4.0 分析仍可用于了解演进过程，但本文以当前源码、SQL 和实测结果为准。

## 1. 摘要

v1 服务端已经完成一条完整的在线即时通信链路：

```text
注册/登录
  → 分配 ChatServer
  → 建立 TCP 长连接
  → 搜索用户
  → 申请好友
  → 认证好友
  → 在线文本聊天
  → 双 ChatServer 跨节点转发
```

v1 的架构重点不是单一 Web 服务，而是多个职责不同的进程：

- GateServer 处理浏览器式 HTTP 请求和认证入口。
- VerifyServer 负责邮箱验证码。
- StatusServer 负责 Token 和聊天节点分配。
- ChatServer/ChatServer2 负责长连接、好友状态和在线消息。
- MySQL 保存用户、好友申请和好友关系。
- Redis 保存在线状态、Token、验证码和公开资料缓存。

真实 `config.ini/config.json` 不进入版本库，仓库只提供示例：

ChatServer 配置中包含三类不同地址：

| 配置 | 含义 |
| --- | --- |
| `[SelfServer]Host/Port` | 自己监听的 TCP 地址 |

这些值决定客户端被分配到哪一个 TCP 聊天节点。

## 4. 通信协议

### 4.1 四条通道

| 通道 | 使用方 | 数据形式 | 生命周期 |
| --- | --- | --- | --- |
| HTTP/JSON | 客户端 → GateServer | JSON | 短连接 |
| gRPC/Protobuf | C++/Node 服务之间 | Protobuf | 每调用借用连接 |
| TCP/JSON | 客户端 ↔ ChatServer | 自定义帧 + JSON | 长连接 |
| Redis RESP | 所有服务 → Redis | Redis 命令 | 连接池 |

### 4.2 HTTP 路由

| 方法 | 路径 | 依赖 | 作用 |
| --- | --- | --- | --- |
| `GET` | `/get_test` | 无 | 开发测试 |
| `POST` | `/get_verifycode` | VerifyServer | 发送验证码 |
| `POST` | `/user_register` | Redis、MySQL、libsodium | 注册 |
| `POST` | `/reset_pwd` | Redis、MySQL、libsodium | 重置密码 |
| `POST` | `/user_login` | MySQL、StatusServer、libsodium | 登录和分配聊天节点 |

### 4.3 gRPC 服务

```proto
service VerifyService {
  rpc GetVerifyCode(GetVerifyReq) returns (GetVerifyRsp);
}

service StatusService {
  rpc GetChatServer(GetChatServerReq) returns (GetChatServerRsp);
  rpc Login(LoginReq) returns (LoginRsp);
}

service ChatService {
  rpc NotifyAddFriend(AddFriendReq) returns (AddFriendRsp);
  rpc NotifyAuthFriend(AuthFriendReq) returns (AuthFriendRsp);
  rpc NotifyTextChatMsg(TextChatMsgReq) returns (TextChatMsgRsp);
  // 协议中还定义了未实现的其他 RPC
}
```

### 4.4 TCP 帧

```text
 0        2        4                          4 + len
 +--------+--------+----------------------------+
 | msg_id |  len   |         JSON body          |
 +--------+--------+----------------------------+
   2 字节   2 字节          len 字节
```

- `msg_id`：大端 16 位。
- `len`：JSON 包体字节数，不包含 4 字节头。
- 最大包体：2048 字节。
- 编码：UTF-8 JSON。

### 4.5 TCP 消息 ID

| ID | 名称 | 方向 |
| --- | --- | --- |
| 1005 / 1006 | TCP 登录请求/响应 | 客户端 ↔ ChatServer |
| 1007 / 1008 | 用户搜索请求/响应 | 客户端 ↔ ChatServer |
| 1009 / 1010 | 好友申请请求/响应 | 客户端 ↔ ChatServer |
| 1011 | 好友申请通知 | ChatServer → 客户端 |
| 1013 / 1014 | 好友认证请求/响应 | 客户端 ↔ ChatServer |
| 1015 | 好友认证通知 | ChatServer → 客户端 |
| 1017 / 1018 | 文本消息请求/响应 | 客户端 ↔ ChatServer |
| 1019 | 文本消息通知 | ChatServer → 客户端 |

## 5. 状态存放

### 5.1 状态归属

| 状态 | 主存储 | 缓存/路由 |
| --- | --- | --- |
| 用户资料 | MySQL `user` | Redis `ubaseinfo_` |
| 密码哈希 | MySQL `user.password_hash` | 不缓存 |
| 用户名索引 | MySQL 唯一索引 | Redis `nameinfo_` |
| 好友申请 | MySQL `friend_apply` | 无 |
| 好友关系 | MySQL `friend` | 不缓存 |
| 验证码 | Redis `code_` | Redis 本身 |
| Token | Redis `utoken_` | Redis 本身 |
| 用户所在节点 | Redis `uip_` | Redis 本身 |
| 本地 TCP Session | ChatServer `UserMgr` 内存 | 无 |
| 在线连接数 | Redis `logincount` | Redis 本身 |

### 5.2 Redis Key

| Key | 类型 | 内容 | TTL |
| --- | --- | --- | --- |
| `code_<email>` | String | 验证码 | 600 秒 |
| `utoken_<uid>` | String | Token | 默认 1800 秒 |
| `uip_<uid>` | String | 用户所在 ChatServer 名称 | 当前无 TTL |
| `ubaseinfo_<uid>` | String | 用户公开资料 JSON | 默认 600 秒 |
| `nameinfo_<name>` | String | UID 字符串 | 默认 600 秒 |
| `logincount` | Hash | ChatServer 在线连接数 | 当前无 TTL |

### 5.3 用户缓存模型

```text
ubaseinfo_<uid> = 完整公开资料 JSON
nameinfo_<name> = UID
```

按用户名查询：

```text
nameinfo_<name>
  → UID
  → ubaseinfo_<uid>
  → 用户资料
```

只有一份完整资料，避免两个 key 保存两份 JSON 后发生不一致。

### 5.4 MySQL 表

| 表 | 职责 |
| --- | --- |
| `user` | 用户资料与密码哈希 |
| `user_id` | 单行 UID 发号器 |
| `friend_apply` | 好友申请与状态 |
| `friend` | 双向好友关系与备注 |

## 6. GateServer

### 6.1 模块结构

| 类 | 职责 |
| --- | --- |
| `CServer` | HTTP acceptor |
| `HttpConnection` | Beast 请求读取、响应写回、连接超时 |
| `LogicSystem` | HTTP 路由和业务处理 |
| `VerifyGrpcClient` | 调用验证码服务 |
| `StatusGrpcClient` | 分配聊天节点 |
| `MysqlDao/MysqlMgr` | 用户查询和持久化 |
| `RedisMgr` | 验证码读取 |
| `PasswordHasher` | Argon2id |

### 6.2 请求处理

```text
CServer::StartAccept
  → HttpConnection::Start
  → async_read
  → HandleReq
  → LogicSystem handler
  → WriteResponse
```

HTTP 响应使用短连接，业务错误通常仍为 HTTP 200，错误码放在 JSON `error` 字段。

### 6.3 注册流程

```text
POST /user_register
  → JSON 解析
  → pwd == confirm
  → Redis GET code_<email>
  → 验证码比较
  → PasswordHasher::Hash
  → MySQL CALL reg_user
  → 返回 uid
```

密码只在服务端处理，客户端不生成密码哈希。

### 6.4 登录流程

```text
POST /user_login
  → MySQL 根据 email 读取 password_hash
  → Argon2id 校验
  → gRPC StatusServer.GetChatServer(uid)
  → 返回 host/port/token
```

StatusServer 失败时不返回登录成功。

### 6.5 密码重置

```text
验证码校验
  → 用户名和邮箱匹配
  → Argon2id 新哈希
  → UPDATE user.password_hash
  → 至少影响一行后才成功
```

## 7. VerifyServer

VerifyServer 是 Node.js gRPC 服务，监听 50051。

### 7.1 文件职责

| 文件 | 职责 |
| --- | --- |
| `server.js` | gRPC 服务和验证码流程 |
| `redis.js` | ioredis 客户端 |
| `email.js` | nodemailer SMTP |
| `proto.js` | 加载共享 proto |
| `config.js` | 读取本地配置 |

### 7.2 验证码流程

```text
GetVerifyCode(email)
  → GET code_<email>
  → 存在则复用
  → 不存在则生成 4 位验证码
  → SET code_<email> value EX 600
  → nodemailer 发送
  → 返回 gRPC 响应
```

当前验证码在注册或重置成功后不会主动删除，仍依赖 TTL 过期。

## 8. StatusServer

### 8.1 职责

StatusServer 只负责两个关键决策：

1. 给用户选择一个 ChatServer。
2. 签发并校验登录 Token。

### 8.2 节点选择

```text
读取 [chatservers]Name
  → 逐个读取 logincount.<server>
  → 选择计数最小节点
  → 返回 host/port
```

登录和断线都通过 `HINCRBY` 原子更新计数。

ChatServer 启动时将自身 field 重置为 0，避免进程崩溃后旧计数残留。

### 8.3 Token

Token 使用 Boost UUID 随机生成：

```text
GET uip? 不需要
  → 生成 Token
  → SET utoken_<uid> <token> EX <ttl>
```

配置：

```ini
[Auth]
TokenTtlSeconds = 1800
```

当前 Token 的职责是允许客户端完成聊天服务器认证，不包含 JWT Claims，也没有刷新机制。

## 9. ChatServer

### 9.1 同源双实例

ChatServer 与 ChatServer2 是两份基本相同的源码目录。

v1 暂未合并成一个二进制加两份配置，因此业务代码修改必须同步两份目录。这是已知架构债务。

### 9.2 启动顺序

```text
ConfigMgr
  → AsioIOServicePool
  → logincount.<SelfServer.Name> = 0
  → gRPC ChatService
  → CServer TCP acceptor
  → io_context.run
```

### 9.3 线程模型

| 执行体 | 数量 | 职责 |
| --- | --- | --- |
| Asio IO 线程池 | 接近 CPU 核心数 | TCP 读写、accept 回调 |
| Chat 主 io_context | 1 | acceptor 与信号处理 |
| LogicSystem 工作线程 | 1 | 所有 JSON 业务串行处理 |
| gRPC 服务线程 | 1 | 跨节点通知 |

业务队列的优点：

- 回调处理顺序确定。
- 避免多个业务线程同时修改客户端状态。

代价：

- 任意 Redis/MySQL 操作变慢都会阻塞该节点全部聊天业务。
- 后续高并发需要业务线程池或异步依赖调用。

### 9.4 长连接类

| 类 | 职责 |
| --- | --- |
| `CServer` | 管理 acceptor 和 `session_id → CSession` |
| `CSession` | 单连接读写、帧解析、发送队列 |
| `LogicNode` | 会话和接收消息的逻辑队列元素 |
| `LogicSystem` | 消息队列、注册映射和业务处理器 |
| `UserMgr` | `uid → 本地 Session` |
| `MsgNode` | TCP 消息缓冲和头/包体表示 |

### 9.5 收包

```text
async_read(4 字节头)
  → 解析 msg_id/msg_len
  → 校验 msg_len <= 2048
  → async_read(msg_len)
  → LogicSystem::PostMsgToQue
  → 继续等待下一个头
```

### 9.6 发包

```text
Send(msg, msg_id)
  → 加锁检查发送队列
  → 构造 SendNode
  → 入队
  → 队列原本为空时启动 async_write
  → 写完后发送下一条
```

当前发送队列上限为 1000，存在满队列静默丢弃风险，属于后续可靠性优化项。

### 9.7 业务处理器

`RegisterCallBacks` 只包含五条映射：

```text
1005 → HandleChatLogin
1007 → HandleSearchUser
1009 → HandleAddFriend
1013 → HandleAuthFriend
1017 → HandleTextChatMsg
```

五个函数都定义在 `LogicSystem.cpp`，避免引入新的模块层级。

`DealMsg` 负责：

- 查找处理器。
- 捕获 `json::exception` 和通用 `std::exception`。
- 保证一条非法消息不会终止工作线程。

## 10. Session 身份

TCP 登录成功后：

```cpp
sess->SetUserId(uid);
UserMgr::GetInst()->SetUserSession(uid, sess);
```

业务处理器统一使用：

```cpp
int uid = sess->GetUserId();
```

可信身份边界：

```text
客户端可决定：目标用户、申请说明、消息内容
客户端不可决定：当前操作者是谁
```

文本消息如果携带兼容字段 `from_uid`，必须与 Session UID 一致。

## 11. 用户搜索

```text
1007
  → Session 已登录
  → 输入为纯数字：GetUserByUid
  → 否则：GetUserByName
```

公开资料缓存：

```text
ubaseinfo_<uid>
nameinfo_<name>
```

缓存未命中时查询 MySQL 并重建，缓存 TTL 默认 600 秒。

## 12. 好友申请

```text
A 1009 请求 B
  → 当前用户 A 来自 Session
  → 校验 B 存在
  → 校验 A/B 尚不是好友
  → INSERT friend_apply(A,B,status=0)
  → 查询 Redis uip_<B>
  → 同节点直接通知
  → 跨节点 gRPC NotifyAddFriend
```

好友申请成功以数据库持久化为准。

如果目标离线，申请仍保存在 MySQL，后续登录会加载到申请列表。

## 13. 好友认证

```text
B 1013 请求认证 A
  → 当前同意者 B 来自 Session
  → 请求中的 to_uid 是申请人 A
  → MySQL 事务：
      UPDATE friend_apply
      INSERT friend(B,A)
      INSERT friend(A,B)
  → 通知 A
```

事务避免出现“申请已同意但没有好友关系”的中间状态。

备注字段：

```text
friend.back
```

好友列表 JOIN 会正确读取备注，不再用用户名覆盖。

## 14. 文本聊天

### 14.1 请求校验

```text
1005 已登录
  → to_uid > 0 且不等于自己
  → AreFriends(uid,to_uid)
  → text_array 是数组
  → 每个元素包含字符串 content/unique_id
```

### 14.2 AreFriends

```sql
SELECT COUNT(*)
FROM friend
WHERE (self_id = ? AND friend_id = ?)
   OR (self_id = ? AND friend_id = ?);
```

只有双向记录都存在才允许聊天。

### 14.3 同节点

```text
查询 uip_<to_uid>
  → 等于当前节点名称
  → UserMgr::GetSession(to_uid)
  → 发送 1019
  → A 的 Defer 发送 1018
```

### 14.4 跨节点

```text
查询 uip_<to_uid>
  → 目标节点名
  → ChatGrpcClient::NotifyTextChatMsg
  → 目标 ChatServiceImpl
  → 目标本地 Session 收到 1019
  → 来源节点发送 1018
```

### 14.5 unique_id

`unique_id` 是客户端生成的字符串 UUID。

数字 `msg_id` 字段保留给未来持久化主键，不用于在线协议关联。

## 15. 跨节点 gRPC

### 15.1 连接池

每个 ChatServer 在启动时为 `[PeerServer]Servers` 中的对端建立固定大小连接池，默认 5 个 Stub。

### 15.2 通知

| RPC | 作用 |
| --- | --- |
| `NotifyAddFriend` | 跨节点好友申请通知 |
| `NotifyAuthFriend` | 跨节点好友认证通知 |
| `NotifyTextChatMsg` | 跨节点文本消息通知 |

### 15.3 目标用户离线

目标 ChatServer 查不到本地 Session 时返回 `Uid_Invalid`，不会默认返回成功。

## 16. 在线人数

登录：

```text
HINCRBY logincount <server_name> 1
```

断线：

```text
HINCRBY logincount <server_name> -1
```

启动：

```text
HSET logincount <server_name> 0
```

目的：

- 消除 `HGET → +1 → HSET` 的并发丢更新。
- 避免 ChatServer 崩溃后旧在线数影响 StatusServer 分配。

## 17. 密码认证

### 17.1 注册

```cpp
PasswordHasher::Hash(password, encoded_hash);
```

数据库只保存：

```text
$argon2id$v=19$m=...$salt$hash
```

### 17.2 登录

```cpp
PasswordHasher::Verify(input_password, encoded_hash);
```

### 17.3 服务边界

- libsodium 只链接 GateServer。
- ChatServer 不读取密码哈希。
- Redis 用户资料缓存不保存密码或密码哈希。

## 18. 数据库与缓存

### 18.1 用户唯一约束

```sql
UNIQUE(uid)
UNIQUE(name)
UNIQUE(email)
```

防止并发注册产生重复账号。

### 18.2 好友索引

```sql
friend_apply(to_uid,status,id)
friend(self_id,friend_id) UNIQUE
friend(friend_id,self_id)
```

分别服务：

- 待处理申请查询。
- 正向好友关系。
- `AreFriends` 反向关系。

### 18.3 好友列表查询

一次 `friend JOIN user`，避免 `1 + N` 次查询。

## 19. 成功回包原则

```text
参数校验
  → Session/Token 校验
  → 数据库或 Redis 主操作
  → 设置成功状态
  → Defer 发送响应
```

已检查：

- GateServer 四个业务接口。
- StatusServer 两个 RPC。
- ChatServer 五类客户端消息。
- ChatServer 三类 gRPC 通知。

目标用户离线或持久化失败时不会默认返回成功。

## 23. 风险与架构债务

### 23.1 P1/P2 已知问题

1. 同账号重复登录可能覆盖 UID → Session 映射。
2. 未实现踢人。
3. 没有心跳和自动重连。
4. 发送队列满时消息会静默丢弃。
5. `uip_` 没有独立 TTL。
6. `AreFriends` 每条消息查询一次 MySQL，后续可缓存。
7. ChatServer1/ChatServer2 约有 29 个同源文件，需要合并。
8. 内部 gRPC 未启用认证和加密。
9. HTTP 未启用 HTTPS。
10. 消息没有持久化和可靠投递。
11. 结构化日志、指标和链路追踪尚未接入。

### 23.2 推荐后续顺序

```text
会话生命周期
  → 踢人
  → 同账号在线策略
  → 心跳
  → 重连

网络与数据可靠性
  → 消息持久化
  → 离线消息
  → 发送队列回执
  → AreFriends 缓存

工程化
  → ChatServer 合并
  → 公共基础设施库
  → 可观测性
  → 内部 gRPC TLS/mTLS
```

## 26. 总结

v1 服务端已经形成清晰的多进程在线聊天架构：HTTP 负责认证入口，StatusServer 负责节点分配，ChatServer 负责长连接和在线业务，MySQL 保存关系数据，Redis 保存跨进程路由和短期状态。

当前最大价值是主链路完整且已经通过端到端测试；最大技术债是 ChatServer 双份源码、消息可靠性和会话生命周期。
