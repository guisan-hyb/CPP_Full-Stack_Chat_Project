## 2. 通信协议总览

### 2.1 三条通信通道

| 通道 | 使用方 | 承载 | 特点 |
| --- | --- | --- | --- |
| HTTP/JSON | 客户端 → GateServer | JSON 文本 | 短连接，`Connection: close`，一次请求一次响应 |
| gRPC + protobuf | GateServer → VerifyServer / StatusServer；ChatServer → StatusServer | `message.proto` | 同步阻塞调用，客户端侧使用固定大小连接池 |
| 自定义 TCP 帧 | 客户端 ↔ ChatServer | 4 字节头 + JSON 体 | 长连接，双向，服务端可主动下发 |

> 注意：**ChatServer 的长连接不经过 protobuf**。它使用自己的二进制头 + JSON 体，只有服务端之间的调用才走 gRPC。

### 2.2 proto 定义（`server/proto/message.proto`）

```protobuf
syntax = "proto3";
package message;

service VerifyService {
    rpc GetVerifyCode (GetVerifyReq) returns (GetVerifyRsp) {}
}

service StatusService {
    rpc GetChatServer (GetChatServerReq) returns (GetChatServerRsp) {}
    rpc Login (LoginReq) returns (LoginRsp) {}
}
```

| 消息 | 字段 | 说明 |
| --- | --- | --- |
| `GetVerifyReq` | `string email = 1` | 目标邮箱 |
| `GetVerifyRsp` | `int32 error = 1`、`string email = 2`、`string code = 3` | `code` 字段当前**未被使用**，验证码改由 Redis 传递 |
| `GetChatServerReq` | `int32 uid = 1` | 用户 uid |
| `GetChatServerRsp` | `int32 error`、`string host`、`string port`、`string token` | 分配给用户的 ChatServer 地址 + 一次性 token |
| `LoginReq` | `int32 uid`、`string token` | ChatServer 向 StatusServer 校验长连接身份 |
| `LoginRsp` | `int32 error`、`int32 uid`、`string token` | 校验结果 |

代码生成：`server/CMakeLists.txt` 用 `protoc` + `grpc_cpp_plugin` 生成到 `build/generated/`，打包为静态库 `chat_proto`，三个 C++ 服务统一链接它；Node 端 `proto.js` 用 `@grpc/proto-loader` 动态加载**同一个** `.proto` 文件。

### 2.3 TCP 长连接帧格式

```
 0        1        2        3        4                      4+len
 +--------+--------+--------+--------+------------------------+
 |      msg_id (2B)  |     msg_len (2B) |   body (msg_len B) |
 +--------+--------+--------+--------+------------------------+
       大端序（网络字节序）               UTF-8 JSON 字符串
```

| 字段 | 长度 | 字节序 | 说明 |
| --- | --- | --- | --- |
| `msg_id` | 2 字节 | 大端 | 消息类型，见 2.5 |
| `msg_len` | 2 字节 | 大端 | body 字节数，上限 `MAX_LENGTH = 2048` |
| `body` | `msg_len` 字节 | — | 当前仅有登录请求/响应的 JSON |

- 服务端：`MsgNode`/`SendNode` 用 `host_to_network_short` 转换；`CSession::HandleReadHead` 用 `network_to_host_short` 还原。
- 客户端：`TcpMgr::slot_send_data` 显式 `QDataStream::BigEndian` 写入；接收侧 `QDataStream` 使用默认大端，恰好与服务端一致。

**MySQL（schema = `guisan`）**

库里只有两张表：`user`（业务数据）和 `user_id`（uid 发号器）。

`user` 表——由线上库导出的真实结构：

| 字段 | 类型 | Null | Key | Extra | 说明 |
| --- | --- | --- | --- | --- | --- |
| `id` | `int` | NO | PRI | `auto_increment` | 物理主键，业务上**未被使用** |
| `uid` | `int` | NO | — | — | 业务用户 ID，登录/鉴权/长连接全用它 |
| `name` | `varchar(255)` | NO | — | — | 用户名，注册时查重 |
| `email` | `varchar(255)` | NO | — | — | 邮箱，登录时作为账号 |
| `pwd` | `varchar(255)` | NO | — | — | 经过客户端 `xorString` 处理后的密文 |

注意 `uid` **不是自增列**，`id` 才是自增但是个"陪跑"的物理主键。业务 ID 由另一张表发放：

`user_id` 表——单行计数器：

| 字段 | 类型 | Null | Key | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `int` | NO | PRI | 当前已发放的最大 uid，无自增属性，只有一行 |

存储过程 `reg_user(IN new_name, IN new_email, IN new_pwd, OUT result)` 的真实逻辑：

```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION  BEGIN ROLLBACK; SET result = -1; END;
START TRANSACTION;
  IF EXISTS (SELECT 1 FROM `user` WHERE `name` = new_name)  THEN SET result = 0;  COMMIT;   -- 用户名重复
  ELSE IF EXISTS (SELECT 1 FROM `user` WHERE `email` = new_email) THEN SET result = 0; COMMIT;  -- 邮箱重复
  ELSE
      UPDATE `user_id` SET `id` = `id` + 1;                 -- 发号器 +1
      SELECT `id` INTO @new_id FROM `user_id`;              -- 取出新号
      INSERT INTO `user` (`uid`,`name`,`email`,`pwd`) VALUES (@new_id, new_name, new_email, new_pwd);
      SET result = @new_id;                                 -- 成功返回新 uid
      COMMIT;
  END IF;
```

`result` 的三种取值，以及 GateServer 对它们的处理：

| `result` | 含义 | GateServer 的处理 |
| --- | --- | --- |
| `> 0` | 注册成功，值为新 `uid` | 返回 `error = 0` |
| `0` | 用户名或邮箱已存在 | `if (uid == 0 \|\| uid == -1)` → 统一返回 `1005 User_Exist` |
| `-1` | 存储过程内部异常并已 `ROLLBACK` | 同上，也归类为 `User_Exist` |

> 【注意】`-1` 是"数据库异常回滚"，不是"用户已存在"。GateServer 把两者合并成同一个错误码，所以线上出现 `User_Exist` 时，需要看 MySQL 日志才能区分"真的重名"和"库出错了"。
>
> 【注意】发号采用 `UPDATE user_id SET id = id + 1` 而不是 `AUTO_INCREMENT`，好处是用户 ID 连续且可预测，代价是**这张单行表会成为并发注册的热点**——所有注册事务都要串行化在这一行上（存储过程已用事务 + 行锁保证一致性）。
>
> 上述 DDL 于 2026-10-03 通过 `desc user` / `desc user_id` / `show create procedure reg_user` 从 `192.168.182.129:3306` 直接导出，非推断。

### 2.6 错误码分层

这套系统里有**三套**互不相同的 error 编码，容易混淆，务必区分：

| 来源 | 值 | 含义 |
| --- | --- | --- |
| 客户端 `ErrorCodes`（`client/global.h`） | 0 / 1 / 2 | 本地网络层：`SUCCESS` / `ERR_JSON` / `ERR_NETWORK` |
| 客户端 `TipErr`（`client/global.h`） | 0–6 | 前端表单校验提示 |
| 服务端 `ErrorCodes`（三个 C++ 服务的 `const.h`） | 见下表 | 业务错误 |
| Node `Errors`（`VerifyServer/const.js`） | 0 / 1 / 2 | 仅用于 `/get_verifycode` 的 `error` 字段 |

服务端业务错误码：

| 值 | 名称 | 出现位置 |
| --- | --- | --- |
| 0 | `Success` | 全部 |
| 1001 | `Error_Json` | GateServer（JSON 解析失败） |
| 1002 | `RPC_Failed` | GateServer / ChatServer（gRPC 调用失败） |
| 1003 | `Verify_Expired` | GateServer（Redis 中无验证码） |
| 1004 | `Verify_Code_Error` | GateServer（验证码不匹配） |
| 1005 | `User_Exist` | GateServer（用户名/邮箱已存在） |
| 1006 | `Passwd_Error` | GateServer（两次密码不一致） |
| 1007 | `Email_Not_Match` | GateServer（重置密码时用户名与邮箱不匹配） |
| 1008 | `Passwd_Up_Failed` | GateServer（更新密码失败） |
| 1009 | `Passwd_Invalid` | GateServer（登录密码错误） |
| 1010 | `Token_Invalid` | StatusServer / ChatServer |
| 1011 | `Uid_Invalid` | StatusServer / ChatServer |

客户端的判断逻辑很粗：只比较 `error != 0`，任何非 0 都统一显示"参数错误"或"登录失败, err is N"。**服务端错误码的细分信息目前在 UI 上被丢掉了。**

### 3.3 HttpMgr：请求与分发的完整路径

```mermaid
sequenceDiagram
    participant D as "某个 Dialog"
    participant H as "HttpMgr"
    participant N as "QNetworkAccessManager"
    participant G as "GateServer"

    D->>H: PostHttpReq(url, json, reqId, mod)
    H->>H: QJsonDocument(json).toJson()
    H->>N: _manager.post(request, data)
    Note over H,N: lambda 捕获 shared_from_this() 保证对象存活
    N->>G: HTTP POST
    G-->>N: JSON 响应
    N->>H: reply finished
    alt reply->error() != NoError
        H->>H: emit sig_http_finish(reqId, "", ERR_NETWORK, mod)
    else 正常
        H->>H: emit sig_http_finish(reqId, res, SUCCESS, mod)
    end
    H->>H: slot_http_finish 按 mod 二次分发
    alt mod == MOD_REGISTER
        H-->>D: sig_reg_mod_finish(id, res, err)
    else mod == MOD_RESET
        H-->>D: sig_reset_mod_finish(id, res, err)
    else mod == MOD_LOGIN
        H-->>D: sig_login_mod_finish(id, res, err)
    end
    D->>D: 解析 JSON → 查 _handlers[id] → 执行回调
```

要点：

- `HttpMgr` 不做 JSON 解析，也不做业务判断，只负责"发出去 + 按模块广播回来"。
- 每个对话框在构造函数里用 `initHttpHandlers()` / `initHandlers()` 建立 `_handlers[ReqId] = lambda` 映射表，形成"请求 ID → 回调"的分发表。
- 响应解析统一在对话框的 `slot_xxx_mod_finish` 里：先查 `err`，再 `QJsonDocument::fromJson`，最后 `_handlers[id](jsonDoc.object())`。
- 【风险】`_handlers[id]` 用的是 `QMap::operator[]`，未注册的 id 会自动插入一个空的 `std::function`，调用会抛异常。当前请求与注册一一对应，暂时不会触发。

### 3.4 TcpMgr：长连接的拆包与分发

```mermaid
graph TD
    A["QTcpSocket::readyRead"] --> B["_buffer.append(_socket.readAll())"]
    B --> C{"!_b_recv_pending ?"}
```

- 连接建立：`QTcpSocket::connected` → `sig_conn_success(true)`。

`xorString`（`client/global.cpp`）的实现：

```cpp
std::function<QString(QString)> xorString = [](QString input){
    QString result = input;
    int length = result.length();
    length %= 255;                       // 密钥 = 密码长度
    for (int i = 0; i < input.length(); i++)
        result[i] = QChar(static_cast<ushort>(input[i].unicode() ^ static_cast<ushort>(length)));
    return result;
};
```

【风险】这是**可逆的混淆**而非加密：密钥就是长度，算法公开、无加盐、无随机数。它的作用只是"让明文密码不出现在抓包和日志里"。数据库里存的就是混淆后的字符串，服务端只做字符串比较。

### 4.1 启动与线程模型

```mermaid
graph TD
    M["main()"] --> C1["ConfigMgr::GetInst() 解析 config.ini"]
    C1 --> C2["RedisMgr::GetInst() 立即建立 Redis 连接池"]
```

| 线程 | 数量 | 负责 |
| --- | --- | --- |
| 主线程 `ioc` | 1 | 只做 `accept`（`CServer` 的 acceptor 绑定在主 `ioc` 上） |
| `AsioIOServicePool` 线程 | 2（构造函数默认写 2，注释里是 `hardware_concurrency()`） | 每个 `HttpConnection` 的读写、超时定时器、业务处理 |

`AsioIOServicePool::GetIOService()` 用 `_nextIOService++ % size` 轮询分配，所以连接是**跨线程轮转**的，这保证了单个长耗时 handler 不会阻塞全部连接。

### 4.4 路由表

| 方法 | 路径 | Handler 做什么 |
| --- | --- | --- |
| GET | `/get_test` | 回显全部查询参数（调试用） |
| POST | `/get_verifycode` | 解析 `email` → `VerifyGrpcClient::GetVerifyCode` → 回 `{error, email}` |
| POST | `/user_register` | 校验两次密码 → 取 Redis 验证码 → 查重并入库 → 回 `{error, email, user, passwd, verifycode}` |
| POST | `/reset_pwd` | 取 Redis 验证码 → 校验用户名与邮箱匹配 → `UPDATE user SET pwd` → 回 `{error, email, user, passwd, verifycode}` |
| POST | `/user_login` | `CheckPwd` → `StatusGrpcClient::GetChatServer(uid)` → 回 `{error, email, uid, token, host, port}` |

每个 POST handler 的开头都有一模一样的异常兜底：

```cpp
try { src_root = json::parse(body_str); }
catch (const json::parse_error& e) {
    root["error"] = ErrorCodes::Error_Json;
    beast::ostream(connection->_response.body()) << root.dump();
    return true;          // 注意：即使解析失败也返回 true，HTTP 状态码仍是 200
}
```

【风险】所有业务错误都以 HTTP 200 + `{"error": 100x}` 返回，客户端只看 body 里的 `error`。这对客户端是可用的，但对排查问题、接入通用工具不友好。
【风险】POST 的路由键直接取 `_request.target()`，一旦带上查询串（如 `/user_login?x=1`）就匹配不到路由。

### 4.5 gRPC 连接池设计

`VerifyGrpcClient` 与 `StatusGrpcClient` 用的是同一套手写连接池模式（`server/AsioIOServicePool 架构` 之外的第二个池）：

```mermaid
graph LR
    subgraph POOL["连接池（构造时预创建）"]
        Q["queue&lt;unique_ptr&lt;Stub&gt;&gt;<br/>pool_size = 5"]
        M["mutex"]
        CV["condition_variable"]
        STOP["atomic&lt;bool&gt; _b_stop"]
    end
    CALL["业务线程"] -->|GetConnection| Q
    Q -->|空则 wait| CV
    CALL -->|RPC| STUB["Stub::Method()"]
    STUB -->|ReturnConnection| Q
    Q -->|notify_one| CV
```

- 构造时创建 5 个 `Stub` 放入队列（`grpc::CreateChannel` 在此处建立，但真正的 TCP 连接是首次 RPC 时惰性发起）。
- `GetConnection()` 在队列为空且未停止时阻塞等待；`_b_stop` 时返回 `nullptr`。
- `ReturnConnection()` 把 stub 放回并 `notify_one()`。
- 两个 `Stub` 类型不同（`VerifyService::Stub` / `StatusService::Stub`），所以各自实现了一份，代码高度重复。
- 【风险】`StatusGrpcClient::GetChatServer` / `Login` 没有判空 `stub`，池已停止时会解引用空指针。
- 【风险】`RPC_connect_pool` 的 `GetConnection` 没有超时，池耗尽时业务线程会无限等待。

### 4.6 数据访问层

**Redis（`RedisMgr`）**：redis++，连接池 5，`connect_timeout` / `socket_timeout` 都是 100ms，连接生命周期 5 分钟（自动重连）。封装了 String（`Get/Set/Del/ExistsKey`）、List（`LPush/LPop/RPush/RPop`）、Hash（`HSet/HGet/HDel`）三组操作。当前业务**只用到 `Get`**（读 `code_<email>`）。

**MySQL（`MysqlDao`）**：使用 mysql-connector-cpp 的 **X DevAPI**（不是 JDBC 风格 API），连接串形如

```
mysqlx://root:123456@192.168.182.129:33060/guisan
```

连接池由 `mysqlx::Client` 的 `POOL_MAX_SIZE = 5` 管理，`getSession()` 返回的 `Session` 是 RAII 对象，析构即归还连接，因此代码里不需要显式 return：

```cpp
mysqlx::Session sess = _pool->getConnection();   // 借出
sess.sql("SELECT email FROM user WHERE name = ?").bind(name).execute();
// sess 在作用域结束时自动归还
```

注册走存储过程而非 INSERT：

```cpp
sess.sql("CALL reg_user(?,?,?,@result)").bind(name).bind(email).bind(pwd).execute();
mysqlx::SqlResult res = sess.sql("SELECT @result AS result").execute();
int uid = res.fetchOne()[0].get<int>();   // 0 或 -1 视为已存在
```

### 5.2 GetVerifyCode 的处理流程

```mermaid
sequenceDiagram
    participant G as "GateServer"
    participant V as "server.js: GetVerifyCode"
    participant R as "redis.js"
    participant RD as "Redis"
    participant E as "email.js"
    participant M as "smtp.qq.com:465"

    G->>V: gRPC GetVerifyCode(email)
    V->>R: GetRedis("code_" + email)
    R->>RD: GET code_email
    RD-->>R: 值 或 null
    R-->>V: uniqueId
    alt Redis 中已有未过期的验证码
        V->>V: 复用旧验证码（不刷新 TTL）
    else 没有缓存
        V->>V: uuidv4() 取前 4 位
        V->>R: SetRedisExpire(code_email, code, 600)
        R->>RD: SET code_email code EX 600
        RD-->>R: OK / 异常
        R-->>V: true / false
        alt 写 Redis 失败
            V-->>G: { email, error: RedisErr }
        end
    end
    V->>E: SendMail(from, to, subject, text)
    E->>M: SMTP over TLS
    M-->>E: 250 OK
    E-->>V: info.response
    V-->>G: { email, error: Success }
```

实现细节与坑：

- **验证码先查再生成**：同一个邮箱在 600 秒内重复点击"获取验证码"，会收到**同一封验证码**，而不是新码。这本身是合理设计，但配合下一条会出问题。
- **重发不刷新 TTL**：复用分支只做 `substring(0, 4)`，没有重新 `SETEX`。所以第 9 分钟重发，验证码仍会在第 10 分钟失效。
- **TTL 与文案不一致**：`SetRedisExpire(..., 600)` 是 10 分钟，但邮件正文写的是"请三分钟内完成注册"。
- **发件人写了两遍**：`server.js` 里 `from: '3550828344@qq.com'` 是硬编码，`email.js` 的 `auth.user` 来自 `config.json`；两处必须同时改才不会出错。
- **Redis 故障不致命**：`GetRedis` 捕获异常后返回 `null`，于是会走"生成新码"分支，再由 `SetRedisExpire` 返回 `false` 触发 `RedisErr(=1)`，服务不会崩。
- **MySQL 配置是死配置**：`config.json` 里有 `mysql` 段，但 `VerifyServer` 全程没有使用数据库。

### 6.4 现状与风险

- 【风险】**token 只存在内存里**：`_tokens` 是进程内 `unordered_map`，StatusServer 一重启，所有已登录用户的长连接 token 全部失效；也不支持多实例部署（第二个实例查不到第一个签发的 token）。
- 【风险】**token 永不过期**：没有 TTL、没有一次性消费、没有清理，uid 再次登录会用新 token 覆盖旧值。
- 【风险】**负载均衡没有真正生效**：`ChatServer::conn_count` 初始化为 0 后**从未被更新**，`getChatServer()` 又用 `minServer = _servers.begin()->second` 起手再逐个比较 `<`，所以结果永远是遍历顺序里的第一台。8991 上那台 chatserver2 实际不会被分配。
- 【风险】`_servers` 为空时 `_servers.begin()->second` 是未定义行为（配置缺失会直接崩）。
- 【半成品】`MysqlMgr`、`MysqlDao` 被编译进 StatusServer 并参与链接，但 `RunServer()` 里没有任何地方创建它们；`RedisMgr` 只在 `main()` 的收尾/异常分支里被 `GetInst()->Close()` 顺带构造，业务上未使用。
- 【半成品】`const.h` 里预留了 `uip_` / `utoken_` / `ipcount_` / `ubaseinfo_` / `logincount` / `lockcount` 等键前缀，配套的限流、单点登录、Redis 版 token 逻辑全部注释未实现。

## 7. ChatServer（C++ / Boost.Asio 长连接服务）

### 7.1 启动与线程模型

```mermaid
graph TD
    M["main()"] --> C1["ConfigMgr::GetInst()"]
    C1 --> C2["AsioIOServicePool::GetInst()<br/>线程数 = std::thread::hardware_concurrency()"]
    C2 --> C3["net::io_context ioc（主循环）"]
    C3 --> C4["signal_set: SIGINT/SIGTERM → ioc.stop() + pool->Stop()"]
    C4 --> C5["CServer server(ioc, 8990)"]
    C5 --> C6["ioc.run()"]

    subgraph POOL["IO 线程池（N = CPU 核数）"]
        P1["io_context[0] + thread"]
        P2["io_context[1] + thread"]
        PN["..."]
    end

    subgraph LOGIC["逻辑线程"]
        LT["LogicSystem::_work_thread ×1"]
        LQ["_msg_que + _cond"]
        LT --- LQ
    end

    C5 -.->|"每个新会话轮询取一个 io_context"| POOL
    POOL -.->|"PostMsgToQue"| LQ
```

三层线程职责清晰：

| 层次 | 线程 | 职责 |
| --- | --- | --- |
| 接受连接 | 主 `ioc` 所在线程 | `CServer::StartAccept()` 递归 `async_accept` |
| 网络读写 | `AsioIOServicePool` 的 N 个线程 | `CSession` 的 `async_read` / `async_write` |
| 业务处理 | `LogicSystem::_work_thread` 单线程 | 从 `_msg_que` 取消息，执行回调（gRPC 调用、查库） |

**关键设计点**：网络线程只做"收字节 + 拆包"，封装成 `LogicNode` 后投递到队列就返回，业务逻辑全部在单线程里串行执行。这避免了给每个会话加锁，也让"同一用户的消息顺序"天然有序；代价是单条业务处理变慢会拖住所有用户。

### 7.2 类职责

| 文件 | 类 | 职责 |
| --- | --- | --- |
| `ChatServer.cpp` | — | 入口：读配置、起线程池、装信号、启动 `CServer` |
| `CServer.*` | `CServer` | `acceptor`（绑定主 `ioc`）+ `unordered_map<string, shared_ptr<CSession>> _sessions` + `_mtx`；`StartAccept` / `ClearSession` |
| `CSession.*` | `CSession` | 单个长连接：UUID、读包头/包体、发送队列、关闭清理 |
| `MsgNode.*` | `MsgNode` / `RecvNode` / `SendNode` | 缓冲区对象；`SendNode` 构造时就拼好 4 字节网络序包头 |
| `LogicSystem.*` | `LogicSystem` | 单例；工作线程 + 消息队列；`RegisterCallBacks()` 注册业务回调；`_users` 做用户信息缓存 |
| `LogicNode`（`CSession.h`） | — | 网络层与逻辑层之间的载体，持有 `CSession` 与 `RecvNode` |
| `StatusGrpcClient.*` | `StatusConnectionPool` + `StatusGrpcClient` | 到 StatusServer 的连接池（5），供 `Login` 使用 |

| `const.h` | — | `ErrorCodes`、`MSG_IDS`、`Defer`（RAII 收尾）、`MAX_LENGTH=2048`、`MAX_SENDQUE=1000` |

### 7.3 收包流程

```mermaid
sequenceDiagram
    participant Sock as "socket"
    participant S as "CSession"
    participant Q as "_msg_que"
    participant L as "LogicSystem 工作线程"

    Note over S: Start() 首次投递 4 字节头读取
    Sock->>S: HandleReadHead(bytes=4)
    S->>S: msg_id = network_to_host_short(head[0..1])
    S->>S: msg_len = network_to_host_short(head[2..3])
    alt msg_id 或 msg_len > MAX_LENGTH
        S->>S: ClearSession + 返回（连接不断）
    else 合法
        S->>Sock: async_read 读取 msg_len 字节
        Sock->>S: HandleReadMsg()
        S->>S: 末尾补 '\0'
        S->>Q: PostMsgToQue(LogicNode{session, recvnode})
        S->>Sock: 重新投递 HandleReadHead（循环）
    end
    Q->>L: _cond.notify_one()
    L->>L: 查 _func_callbacks[msg_id]
    L->>L: 执行回调
```

线程安全的细节值得注意：`PostMsgToQue` 只在"队列从空变为 1"时才 `notify_one()`，这是典型的"只要有一个待处理唤醒即可"的写法；工作线程 `DealMsg` 用 `wait(ulk, predicate)` 避免虚假唤醒。

【风险】`msg_id > MAX_LENGTH` 这个校验把 ID 和长度用了同一个上限，语义上应该是"ID 是否在已知集合内"。不过由于紧接着 `_func_callbacks.find()` 会兜底，目前只是校验不起作用。

### 7.4 发包流程

```mermaid
graph LR
    A["LogicSystem 回调"] -->|"session->Send(msg, msg_id)"| B["_send_mtx 加锁"]
    B --> C{"队列长度 > MAX_SENDQUE(1000) ?"}
    C -- 是 --> D["打印日志并丢弃"]
    C -- 否 --> E["push 一个新 SendNode<br/>（已拼好 4 字节包头）"]
    E --> F{"发送前队列原来是否为空 ?"}
    F -- "否（说明已有写操作在跑）" --> G["直接返回"]
    F -- 是 --> H["DoWrite()"]
    H --> I["async_write 队列首元素"]
    I --> J["成功后 pop，队列非空则递归 DoWrite"]
    I --> K["失败 → ClearSession + Close"]
```

设计要点：**同一个 `CSession` 的发送是严格串行的**，靠"队列非空就不再发起新的 `async_write`"保证；每个 `SendNode` 在构造时就写好网络序的 `msg_id`/`msg_len`，写出去的内容和队列里的对象一一对应。

### 7.5 长连接登录的完整处理

```mermaid
sequenceDiagram
    participant C as "Qt 客户端 TcpMgr"
    participant S as "CSession"
    participant L as "LogicSystem 工作线程"
    participant SS as "StatusServer"
    participant DB as "MySQL"

    Note over C,S: 之前已由 /user_login 拿到 host=127.0.0.1 port=8990 token
    C->>S: TCP 三次握手（QTcpSocket::connectToHost）
    S-->>C: connected → 客户端 emit sig_conn_success(true)
    C->>S: 帧 id=1005, body={"uid":N,"token":"..."}
    S->>L: PostMsgToQue
    L->>L: 命中 MSG_CHAT_LOGIN 回调
    L->>L: json::parse(body) 取 uid / token
    L->>SS: gRPC Login(uid, token)
    alt token 非法
        SS-->>L: error = 1010 / 1011
        L-->>S: Defer 触发 Send(json, 1006)  {"error":1010}
        S-->>C: 客户端 emit sig_login_failed(1010) → 提示登录失败
    else token 有效
        SS-->>L: error = 0
        L->>L: 查 _users[uid] 缓存
        alt 缓存未命中
            L->>DB: SELECT uid,name,email,pwd FROM user WHERE uid = ?
            DB-->>L: 用户行
            L->>L: _users[uid] = user_info
        end
        L-->>S: Defer 触发 Send(json, 1006)<br/>{"error":0,"uid":N,"token":"...","name":"xxx"}
        S-->>C: TcpMgr 回调写入 UserMgr
        C->>C: emit sig_switch_chatDlg()（当前无接收者）
    end
```

注意 `Defer` 的用法——它保证了**任何一条 return 路径都会把响应发出去**：

```cpp
Defer defer([&root, this, sess] {
    std::string jsonstr = root.dump();
    sess->Send(jsonstr, MSG_CHAT_LOGIN_RSP);
});
root["error"] = rsp.error();
if (rsp.error() != ErrorCodes::Success) return;   // 这里也会触发上面的 lambda
```

【已修复】`json::parse` 失败的分支原先只打印日志、没有 `return`，随后 `src_root["uid"].get<int>()` 抛出的 `nlohmann::json` 异常会穿过 `DealMsg()`（其内部没有 catch），直接 `std::terminate` 掉整个 ChatServer。2026-10-03 已在 `LogicSystem.cpp` 第 83 行补上 `return;`，崩溃风险消除。

```cpp
		json src_root;
		try {
			src_root = json::parse(msg_data);
		}
		catch (const json::parse_error& e) {
			std::cerr << "LoginHandler parse json error: " << e.what() << std::endl;
			return;                        // ← 新增：解析失败直接放弃这条消息
		}

		auto uid = src_root["uid"].get<int>();
		...
		json root;
		Defer defer([&root, this, sess] {  // ← 第 94 行，注意它在 return 之后
			std::string jsonstr = root.dump();
			sess->Send(jsonstr, MSG_CHAT_LOGIN_RSP);
		});
```

【残留问题】这个 `return` 发生在 `Defer` 构造之前，所以畸形报文现在**不会崩，但也不会给客户端任何回包**；而客户端 `TcpMgr` 没有读超时，表现是界面静默卡住。更彻底的写法是把 `Defer` 提到解析之前，让解析失败时也回一个 `{"error": 1001}`，让客户端能明确失败。

### 7.6 Session 管理

| 行为 | 实现 |
| --- | --- |
| 创建 | `CServer::StartAccept` 中 `make_shared<CSession>(pool_io, this)`，UUID 在构造时用 `boost::uuids::random_generator` 生成 |
| 登记 | `async_accept` 成功且 `Start()` 后写入 `_sessions[uuid]`（加 `_mtx`） |
| 注销 | `ClearSession(uuid)` 从 map 移除；在读/写出错、长度非法、`Close()` 的多条路径上被调用 |
| 关闭 | `Close()` 置 `_b_stop = true` 并 `_socket.close()` |
| 【风险】 | `HandleReadHead` 中长度非法时只调了 `ClearSession` 而没有 `Close()`，socket 不会被主动关闭，连接对象可能一直挂着 |

联调通过时应能观察到（服务端与客户端日志）：

1. GateServer 打印 `receive body is: {"email":...,"passwd":...}`，随后 `succeed to load, userinfo is: <uid>`；

| 5 | ChatServer | 客户端长连接的目标；必须在第一次 TCP 连接之前就绪 | `cd build/server/ChatServer/Debug` → `./ChatServer.exe` |
| 6 | GateServer | 客户端的唯一 HTTP 入口 | `cd build/server/GateServer/Debug` → `./GateServer.exe` |
| 7 | Qt 客户端 | 依赖 GateServer 提供 `gate_url_prefix` 指向的地址 | Qt Creator 打开 `client/client.pro` 构建运行 |

**停止顺序**：与启动顺序相反（客户端 → GateServer → ChatServer → StatusServer → VerifyServer → Redis/MySQL），这样能避免客户端在服务重启期间拿到半开连接。

### 9.3 关于"必须按顺序"的两个重要澄清

1. **三个 C++ 服务不会因为下游未启动而拒绝启动**。`VerifyGrpcClient` / `StatusGrpcClient` 的 `Stub` 是"首次 RPC 时才真正建连"，`MysqlMgr` / `ChatServer` 的 MySQL 连接池也是首次调用才创建。所以先起 GateServer 再起 VerifyServer 通常也能跑通，只是**第一笔**验证码请求会失败。
2. **唯一会"启动即建连"的是 GateServer 的 Redis**（`GateServer.cpp` 的 `main()` 里直接调用 `RedisMgr::GetInst();`）。Redis 不可用时它只打印 `Redis connect failed` 并继续运行，之后每次读写都会失败——表现是"注册/重置时永远提示验证码过期"。

### 9.4 两个容易踩的环境问题

**工作目录决定配置文件能否找到。** 三个 C++ 服务的 `ConfigMgr` 都是这样取配置的：

```cpp
std::filesystem::path config_path = std::filesystem::current_path() / "config.ini";
```

即**从当前工作目录**找 `config.ini`，不是从 exe 所在目录。CMake 的 `POST_BUILD` 已把 `config.ini` 拷到 `$<TARGET_FILE_DIR:...>`，所以只要 `cd` 到 exe 目录再执行就正常；如果从仓库根目录直接 `.\build\server\GateServer\Debug\GateServer.exe`，会读不到配置（所有值变空字符串），表现为端口解析异常或连到错误的地址。

**Node 侧不受工作目录影响。** `config.js` 用 `path.join(__dirname, 'config.json')`，从任何目录启动都能正确读到配置（这一点比 `Server架构分析2.0` 记录的问题已经修复）。

### 11.3 建议的下一步

按"先修悬崖、再补功能"的顺序：

1. **清剩下的两个 P0**：把 `config.json` 移出 Git 并重置 QQ 邮箱授权码（它已经躺在提交历史里了）；给 `StatusServiceImpl::getChatServer()` 加空容器判空。

5. **补心跳与重连**：长连接一旦要承载消息，就必须有连接保活与断线恢复。
