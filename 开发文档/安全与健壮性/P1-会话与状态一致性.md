# P1 会话与状态一致性

## 1. 文档目标

本文记录会话和状态一致性相关的 P1 优化，包括：

- 在线人数使用 Redis `HINCRBY` 原子增减。
- ChatServer 启动时重置本节点在线计数。
- Token 增加可配置的 Redis TTL，默认 30 分钟。
- 业务成功回包移动到主要业务操作完成之后。

## 2. 本轮范围

### 2.1 已完成

1. `RedisMgr` 增加 `HIncrBy`。
2. 登录成功时原子增加在线人数。
3. 断线清理时原子减少在线人数。
4. 每个 ChatServer 进程启动时把自己的计数字段重置为 0。
5. StatusServer 签发 Token 时写入 30 分钟 TTL。
6. `[Auth].TokenTtlSeconds` 可以覆盖默认值。
7. 检查并调整当前全部业务处理器的成功回包时机。
8. 扩展端到端测试，校验 Token TTL 和在线计数。

### 2.2 明确不在本轮范围

- 不修复重复登录导致的 UID → Session 映射覆盖问题。
- 不实现同一账号禁止在线共存。
- 不实现踢人功能。
- 不引入分布式锁。
- 不实现 Token 刷新。
- 不实现断线重连。

## 3. 在线人数原问题

原实现使用：

```text
HGET logincount chatserver1
字符串转整数
+1 或 -1
HSET logincount chatserver1 <result>
```

这是一个非原子的“读取—修改—写回”过程。

并发登录或断线时可能出现：

```text
线程 A 读取 5
线程 B 读取 5
线程 A 写回 6
线程 B 写回 6
```

两次登录只增加了 1，在线计数偏低，随后 StatusServer 可能把更多用户分配到已过载的节点。

## 4. RedisMgr 增加 HIncrBy

### 4.1 接口

保持现有 RedisMgr 的 `bool + 输出参数` 风格：

```cpp
bool HIncrBy(
    const std::string& key,
    const std::string& field,
    long long increment,
    long long& value);
```

返回值：

- `true`：Redis 命令执行成功。
- `false`：连接、超时或 Redis 命令异常。
- `value`：增长或减少后的新值。

### 4.2 实现

```cpp
value = _redis->hincrby(key, field, increment);
```

Redis 本身保证 `HINCRBY` 原子执行，因此不需要应用层锁。

### 4.3 登录增加计数

ChatServer 登录成功后：

```cpp
long long conn_count = 0;
if (!RedisMgr::GetInst()->HIncrBy(
        std::string(LOGIN_COUNT),
        server_name,
        1,
        conn_count)) {
    root["error"] = ErrorCodes::RPC_Failed;
    return;
}
```

只有 Redis 原子递增成功，才继续绑定 Session UID 和用户在线节点。

### 4.4 断线减少计数

`CServer::ClearSession` 确认该 Session 已执行过登录后：

```cpp
RedisMgr::GetInst()->HIncrBy(
    std::string(LOGIN_COUNT),
    server_name,
    -1,
    conn_count);
```

如果 Redis 操作失败，只记录错误，不能阻止本地 Session 清理。

### 4.5 为什么不需要分布式锁

在线人数只需要单个计数器操作，`HINCRBY` 本身已经原子，不需要再包一层分布式锁。

本轮没有引入分布式锁。后续踢人功能如果需要原子执行“检查旧 Session、关闭旧连接、替换映射”，应重新设计对应的一致性方案。

## 5. 节点启动时重置在线计数

进程异常退出时，本地 Session 全部丢失，但 Redis 中的计数字段可能残留旧值。

ChatServer 启动时执行：

```cpp
RedisMgr::GetInst()->HSet(
    std::string(LOGIN_COUNT),
    server_name,
    "0");
```

每个节点只重置自己的字段：

```text
chatserver1 启动 → logincount.chatserver1 = 0
chatserver2 启动 → logincount.chatserver2 = 0
```

不会影响另一节点的计数。

测试时先写入：

```text
chatserver1 = 99
chatserver2 = 88
```

启动两个 ChatServer 后实际确认：

```json
{"chatserver1":"0","chatserver2":"0"}
```

## 6. Token TTL

### 6.1 原问题

原来 Token 使用普通 `SET` 写入 Redis：

```text
utoken_<uid> = <token>
```

没有过期时间，Token 会永久保留，直到同一用户再次登录覆盖。

### 6.2 默认 TTL

默认：

```text
1800 秒 = 30 分钟
```

配置项：

```ini
[Auth]
TokenTtlSeconds = 1800
```

配置读取位置：

```text
server/StatusServer/StatusServiceImpl.cpp
```

缺失时使用 1800 秒；配置非法时记录错误并回退到 1800 秒。

### 6.3 RedisMgr 增加 SetWithExpire

接口：

```cpp
bool SetWithExpire(
    const std::string& key,
    const std::string& value,
    std::chrono::seconds ttl);
```

实现：

```cpp
_redis->set(key, value, ttl);
```

Redis 会原子写入值和 TTL。

### 6.4 Token 签发流程

```text
生成随机 Token
  → SET utoken_<uid> <token> EX <ttl>
  → 写入成功后设置 response.error = Success
  → GateServer 返回 Token、ChatServer 地址
```

如果 Redis 写入失败：

```text
response.error = RPC_Failed
gRPC 返回 CANCELLED
```

不会向客户端返回一个没有实际写入 Redis 的 Token。

### 6.5 TTL 验证

测试登录后执行：

```text
TTL utoken_<uid>
```

本次测试结果位于：

```text
0 < TTL <= 1800
```

30 分钟针对的是“从 HTTP 登录到建立 TCP 聊天连接”的认证窗口。

当前没有 Token 刷新和重连机制，因此这不会影响已经建立并持续保持的 Session。

## 7. 成功回包时机

### 7.1 统一原则

所有业务处理器遵循：

```text
参数校验
  → Session/Token 校验
  → 数据库或 Redis 主操作
  → 构造业务结果
  → 设置 error = Success
  → Defer/函数出口发送响应
```

不能因为“即将执行”就提前返回成功。

### 7.2 GateServer

| 接口 | 成功条件 |
| --- | --- |
| `/get_verifycode` | Verify gRPC 成功 |
| `/user_register` | Argon2id 成功，`reg_user` 返回有效 UID |
| `/reset_pwd` | 用户邮箱匹配，密码更新影响至少一行 |
| `/user_login` | 密码校验通过，StatusServer 成功返回 ChatServer 和 Token |

### 7.3 StatusServer

| 接口 | 成功条件 |
| --- | --- |
| `GetChatServer` | 选择节点成功，Token 带 TTL 写入 Redis 成功 |
| `Login` | Redis Token 存在且匹配 |

### 7.4 ChatServer 客户端业务

| 消息 | 成功条件 |
| --- | --- |
| 1005 聊天登录 | Token 校验、用户信息读取、在线计数和 UID 在线节点写入完成 |
| 1007 用户搜索 | 找到用户并构造完整结果 |
| 1009 好友申请 | 目标存在、非好友，申请持久化成功 |
| 1013 好友认证 | 申请事务提交成功 |
| 1017 文本消息 | 身份与好友关系通过，且同服发送或跨服 RPC 返回成功 |

### 7.5 ChatServer 内部 gRPC

| RPC | 成功条件 |
| --- | --- |
| `NotifyAddFriend` | 目标 Session 存在并完成通知入队 |
| `NotifyAuthFriend` | 目标 Session 存在，发送者资料读取成功 |
| `NotifyTextChatMsg` | 目标 Session 存在并完成文本通知入队 |

目标用户不在当前 ChatServer 时，返回 `Uid_Invalid`，不再默认回成功。

## 8. 登录计数回滚

登录过程中依次执行：

```text
HINCRBY +1
SET uip_<uid> <server>
Session SetUserId
UserMgr SetUserSession
设置成功
```

如果 `uip_<uid>` 写入失败，会执行：

```text
HINCRBY -1
```

避免登录未完成但在线计数已经增加。

## 11. 已知边界

- 重复登录仍可能覆盖 UID → Session 映射，故意不在本轮修复。
- 在线人数表示连接数，不代表唯一账号数。
- 分布式锁未引入。
- Token 过期后当前实现会要求重新登录，暂无刷新流程。
- 好友申请/认证成功以数据库持久化为准；如果在线通知失败，申请数据仍然存在。
- 文本消息成功回包表示目标 ChatServer 已接受通知，不等价于接收端客户端已阅读。
