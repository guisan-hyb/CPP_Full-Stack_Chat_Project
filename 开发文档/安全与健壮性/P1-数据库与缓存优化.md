# P1 数据库与缓存优化

## 1. 文档目标

本文记录好友数据查询、数据库索引和用户资料缓存的 P1 优化，包括：

- 修复好友列表备注 `back` 被用户名覆盖的问题。
- 将好友列表 N+1 查询改为一次 `JOIN`。
- 去除好友查询中的 `SELECT *`。
- 为用户、好友申请和反向好友查询补充索引。
- 统一用户资料缓存模型。
- 为用户公开资料缓存增加默认 600 秒 TTL。

## 2. 原问题概览

### 2.1 好友备注读取后未使用

原代码：

```cpp
auto back = row[3].isNull() ? "" : row[3].get<std::string>();
auto user_info = GetUser(friend_id);
user_info->back = user_info->name;
```

虽然读取了 `friend.back`，但最终又把备注覆盖成好友用户名。

结果是：

- 用户添加好友时填写的备注无法正确返回。
- 好友列表总是显示用户名，而不是自定义备注。

### 2.2 好友列表 N+1 查询

原流程：

```text
查询 friend：1 次
遍历每条好友关系再调用 GetUser：N 次
总查询次数 = 1 + N
```

好友越多，数据库访问次数越多。

### 2.3 `SELECT *` 导致字段位置脆弱

原查询：

```sql
SELECT *
FROM friend
WHERE self_id = ?;
```

随后依赖 `row[2]`、`row[3]` 等固定下标。数据库新增列或调整列顺序时，代码容易读取错误字段。

### 2.4 用户资料缓存保存两份完整副本

原缓存：

```text
ubaseinfo_<uid>  = 完整用户 JSON
nameinfo_<name>  = 完整用户 JSON
```

问题：

- 同一用户资料保存两次。
- 修改昵称、头像或简介时需要同步更新两个 key。
- 名称搜索和 UID 搜索走两套独立解析逻辑。
- 任一路径漏更新都会产生缓存不一致。

### 2.5 用户缓存没有 TTL

原缓存使用普通 `SET`，用户资料会一直保留，直到重新写入或手工删除。

可能导致：

- 用户资料修改后旧缓存长期存在。
- Redis 中积累不再活跃的用户资料。

## 3. 好友列表查询优化

### 3.1 新查询

ChatServer 与 ChatServer2 都改为一次 JOIN：

```sql
SELECT
    u.uid,
    u.name,
    u.email,
    u.nick,
    u.`desc`,
    u.sex,
    u.icon,
    f.back
FROM friend f
JOIN user u ON u.uid = f.friend_id
WHERE f.self_id = ?
ORDER BY f.id ASC;
```

查询次数：

```text
1 次 JOIN 查询
```

不再在循环中调用 `GetUser(friend_id)`。

### 3.2 正确返回备注

```cpp
user_info->back = row[7].isNull() ? "" : row[7].get<std::string>();
```

`back` 直接来自好友关系表，不再被 `user_info->name` 覆盖。

### 3.3 明确返回列

代码不再使用 `SELECT *`，而是显式列出：

```text
uid
name
email
nick
desc
sex
icon
back
```

数据库字段位置和业务结构建立明确对应关系。

## 4. 数据库索引

新增迁移：

```text
server/sql/migrations/002_database_cache_indexes.sql
```

### 4.1 用户唯一索引

```sql
ALTER TABLE user
    ADD UNIQUE KEY uk_user_uid (uid),
    ADD UNIQUE KEY uk_user_name (name),
    ADD UNIQUE KEY uk_user_email (email);
```

作用：

- 防止并发注册产生重复 UID、用户名或邮箱。
- 让按 UID、名称、邮箱查询使用索引。
- 为注册存储过程增加数据库级最终约束。

此前 `reg_user` 中先查询再插入，没有唯一索引时，两次并发注册仍可能同时通过存在性检查。

### 4.2 好友申请收件索引

```sql
ALTER TABLE friend_apply
    ADD KEY idx_apply_recipient (to_uid, status, id);
```

支持：

```sql
WHERE to_uid = ?
  AND id > ?
ORDER BY id
```

### 4.3 反向好友查询索引

```sql
ALTER TABLE friend
    ADD KEY idx_friend_reverse (friend_id, self_id);
```

`AreFriends` 需要同时查询：

```text
(self_id = A, friend_id = B)
(self_id = B, friend_id = A)
```

正向查询使用：

```text
UNIQUE(self_id, friend_id)
```

反向查询使用新增索引。

### 4.4 实际索引结果

当前库确认存在：

```text
user:        PRIMARY, uk_user_uid, uk_user_name, uk_user_email
friend_apply: PRIMARY, from_to, idx_apply_recipient
friend:      PRIMARY, self_friend, idx_friend_reverse
```

### 4.5 执行计划

好友列表 JOIN 实测：

```text
friend 表：使用 self_friend 索引
user 表：使用 uk_user_uid 索引
```

原先每个好友一次用户查询，现在变成一次索引 JOIN。

## 5. 统一用户资料缓存

### 5.1 新缓存模型

```text
ubaseinfo_<uid> = 用户公开资料 JSON
nameinfo_<name> = UID 字符串
```

示例：

```text
ubaseinfo_1001 = {
  "uid": 1001,
  "name": "alice",
  "email": "...",
  "nick": "...",
  "desc": "...",
  "sex": 1,
  "icon": "..."
}

nameinfo_alice = "1001"
```

### 5.2 为什么名称索引只保存 UID

一个用户只需要保存一份完整资料。

名称只是检索入口：

```text
用户名 → UID → 用户资料
```

这样修改昵称、头像、简介时只需要更新 `ubaseinfo_<uid>`，不需要同步两份完整 JSON。

### 5.3 按 UID 查询

```text
查询 ubaseinfo_<uid>
  → 命中：反序列化并返回
  → 未命中：MySQL 查询
  → 写入带 TTL 的资料缓存
  → 写入带 TTL 的名称索引
```

### 5.4 按用户名查询

```text
查询 nameinfo_<name>
  → 得到 UID
  → 查询 ubaseinfo_<uid>
  → 命中后校验资料中的 name 与搜索名称一致
  → 返回用户资料
```

如果名称索引不存在、不是合法 UID，或对应资料名称不一致：

```text
MySQL 按 name 查询
  → 重建 ubaseinfo_<uid>
  → 重建 nameinfo_<name>
```

### 5.5 旧缓存兼容

旧版本 `nameinfo_<name>` 保存完整 JSON，新版本期望 UID 字符串。

本次采用直接切换，不做旧格式解析兼容。部署时需要删除一次旧 key：

```text
nameinfo_*
ubaseinfo_*
```

当前测试环境已清理这些 key。

## 6. 用户缓存 TTL

### 6.1 配置

默认：

```ini
[Cache]
UserProfileTtlSeconds = 600
```

配置位置：

```text
server/ChatServer/config.example.ini
server/ChatServer2/config.example.ini
```

缺失时使用 600 秒；非法配置时记录错误并回退到 600 秒。

### 6.2 RedisMgr 方法

ChatServer 的 RedisMgr 新增：

```cpp
bool SetWithExpire(
    const std::string& key,
    const std::string& value,
    std::chrono::seconds ttl);
```

资料缓存和名称索引使用同一个 TTL，确保两者大致同时过期。

### 6.3 固定 TTL

当前采用固定 TTL，不在每次读取时续期。

这样即使缓存访问频繁，也会按固定周期回到 MySQL 获取最新公开资料。后续如果有资料编辑功能，还应增加显式缓存失效。

## 9. 当前边界

- 好友列表暂未分页，继续沿用当前设计。
- 用户资料缓存是固定 TTL，不做滑动续期。
- 当前没有用户资料编辑接口，因此暂未加入主动失效调用。
- 用户资料缓存仍包含邮箱字段；后续如果重新定义公开资料，可统一裁剪。
- Redis 缓存和 MySQL 更新不是跨存储事务。
- 本轮没有引入分布式锁。
