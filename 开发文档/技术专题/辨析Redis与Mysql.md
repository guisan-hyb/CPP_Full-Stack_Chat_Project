## 辨析Redis与Mysql

你的直觉极其准确！用“内存”和“硬盘文件”来概括两者最本质的区别，抓住了核心。基于你对通俗比喻和架构应用的偏好，我们不看枯燥的底层源码，直接用**“开公司”**的比喻，把你脑海中的概念彻底打通。

---

### 一、 通俗比喻：前台工位 vs 地下室档案室

想象你的后端系统是一家公司：

**MySQL —— 地下室档案室**

* **特点**：容量极大，永久保存。但每次找档案都要走到地下室，翻阅目录，再拿回前台，速度比较慢。
* **规矩严格**：档案必须按照特定的表格格式填写（关系型数据库，表结构）。如果要查“年龄大于18岁的员工”，档案室管理员可以帮你精准筛出来。
* **安全性极高**：就算突然停电，档案室里的资料也不会丢（持久化）。

**Redis —— 前台工位上的便签本**
* **特点**：容量小（工位面积有限），但随手就能拿到，速度极快（纳秒/微秒级）。
* **规矩灵活**：便签本上可以随便画画（数据结构灵活：String、List、Hash都行），不用填正规表格。
* **易失性**：如果公司突然停电，便签本上的字可能就模糊甚至没了（内存断电丢失）。虽然可以拿去复印（RDB/AOF持久化），但依然有丢失最新几秒数据的风险。

---

### 二、 架构应用：为什么要“双剑合璧”？

你提到“邮箱可以放Redis，用户信息放MySQL”。这个思路已经很接近标准架构了！但在实际工程中，我们要解决一个核心矛盾：**MySQL太慢，Redis太快但易失。**

业界标准的架构模式叫做 **Cache-Aside（旁路缓存模式）**。我们以你的聊天项目“查询用户信息”为例：

#### 1. 标准的“读”架构（查用户信息）
当 GateServer 收到请求，要查 ID 为 1001 的用户信息：
1. **先翻便签**：去 Redis 查 `user:1001`。
2. **便签上有（缓存命中）**：直接返回数据。速度快，且没打扰地下室管理员。
3. **便签上没有（缓存未命中）**：没办法，只能去 MySQL 查。
4. **抄回便签**：从 MySQL 查到数据后，顺便在 Redis 里也写一份（设个过期时间，比如1小时）。
5. 下次再查 1001，就能直接读便签了。

#### 2. 标准的“写”架构（修改用户信息，比如改昵称）
千万不能只改 Redis！如果只改便签，地下室档案还是旧的，一停电便签丢了，昵称就变回去了。
正确顺序是：
1. **先更新档案室**：去 MySQL `UPDATE` 昵称。
2. **再撕掉便签**：去 Redis `DEL user:1001`。（注意：是删除缓存，而不是更新缓存。下次有人查时，会自动去 MySQL 拉最新的填回便签）。

### 三、 回答你的第二个问题：邮箱、用户信息到底怎么放？

你说“邮箱放Redis，用户信息放MySQL”，在实际架构中，我们会稍微调整一下，让它们更科学：

**1. 关于邮箱（用于查重和登录）**
* **MySQL 是底线**：必须在 MySQL 的 `users` 表里建一个 `email` 字段，并加上 `UNIQUE KEY`（唯一索引）。这是为了防止两个用户注册同一个邮箱。
* **Redis 是盾牌**：为了不让高频的注册请求把 MySQL 压垮，可以在 Redis 里存一个 `email_exist:xxx@qq.com` 的标记。注册时先看 Redis，如果有直接拒绝。如果没有再去查 MySQL。
* **总结**：邮箱真实数据必须在 MySQL，Redis 只是用来加速拦截。

**2. 关于用户信息（昵称、头像、等级）**
* **MySQL 存全量**：所有人的所有信息，永久存放在 MySQL。
* **Redis 存热点**：只把**经常被查询的活跃用户**信息，打包成一个 Hash 结构，缓存在 Redis 里。不活跃的用户数据不需要放 Redis，浪费内存。

### 四、 架构师必须知道的“三大缓存暗坑”（面试必考）

既然引入了 Redis 当缓存，架构上就会带来三个经典的“暗坑”，你在开发全栈项目时一定会遇到：

#### 坑1：缓存穿透
* **场景**：黑客拿一个根本不存在的邮箱（比如 `aaa@bbb.com`）疯狂发登录请求。Redis 里没有，请求全打到 MySQL。MySQL 里也没有，查了半天空手而回。MySQL 被活活累死。
* **解药**：如果 MySQL 查不到，也在 Redis 里存一个特殊的标记（比如 `email:aaa@bbb.com -> "NULL"`，设很短的过期时间）。下次黑客再来，Redis 直接返回“不存在”，挡住 MySQL。

#### 坑2：缓存击穿
* **场景**：某个超级热门的用户（比如大V）数据存在 Redis 里，突然过期时间到了，便签被撕了。这一瞬间，成千上万个请求同时来查他，全扑向了 MySQL，MySQL 瞬间崩溃。
* **解药**：给热点数据设置“永不过期”，或者让第一个去查 MySQL 的线程加一个“分布式锁”，其他线程等它查完写回 Redis 后再读 Redis。

#### 坑3：缓存雪崩
* **场景**：你给一万个用户的缓存都设置了“1小时后过期”。结果恰好在第61分钟，网站迎来晚高峰，一万个用户的便签同时失效，请求如雪崩般砸向 MySQL。
* **解药**：给过期时间加一个随机值（比如 1小时 ± 10分钟），让便签错峰失效。

### 总结
作为架构师，你要记住一句口诀：**“Redis 决定速度，MySQL 决定底线。”**
所有的核心业务逻辑（扣钱、注册、建号）必须以 MySQL 为准；所有的性能优化（快速响应、高并发读取）交给 Redis。把它们用 Cache-Aside 模式组合起来，你的聊天项目后端就具备了真正工业级的抗压能力！
