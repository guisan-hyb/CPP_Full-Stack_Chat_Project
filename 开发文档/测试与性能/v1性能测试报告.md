# v1 性能测试报告

## 0. 结论摘要

测试日期：2026-10-24

被测版本：`feature/v1收尾`，提交 `cd32ad1`

测试对象：Windows Release 版 v1 服务端，MySQL/Redis 运行在 Linux VM 的隔离容器中。

本次在 100 个用户、50 对好友、64 字节文本消息下完成分级测试：

- 所有正式阶段成功率为 100%，没有协议错误或超时。
- 结束后 Redis 在线计数回到 0。
- HTTP `/get_test` 在 100 并发下约 2802 req/s，p95 为 44ms。
- HTTP 登录在 100 并发下吞吐约 39.4 req/s，但 p95 达到 3511ms。
- 同节点聊天吞吐在 10～50 发送者时稳定在约 1.1k msg/s。
- 跨节点聊天吞吐稳定在约 430 msg/s，明显低于同节点。
- 50 个同节点发送者时 ACK p95 为 94ms，p99 为 254ms。
- 50 个跨节点发送者时 ACK p95 为 222ms，p99 为 432ms。
- MySQL 的 `AreFriends` 查询和 GateServer 的 Argon2id 是当前最明显的两条成本路径。
- 测试中发现：两个用户并发注册时曾出现一次数据库返回 `-1`，随后被 Gate 映射为“用户已存在”1005。正式数据准备因此改为串行注册。

## 3. 测试方法

### 3.1 负载模型

测试使用闭环节奏：每个虚拟用户完成一次请求并收到响应后，立即发起下一次请求，不设置思考时间。结果用于比较系统上限，不代表真实用户聊天节奏。

压测器：

```text
server/tests/v1_perf_test.js
```

压测器使用 Node.js 内置的 `http` 和 `net`，不依赖第三方压测库。

### 3.2 阶段与压力

| 阶段 | 并发档位 | 每档时长 |
| --- | --- | --- |
| HTTP 注册 | 1 | 100 次注册 |
| HTTP `/get_test` | 1 / 10 / 50 / 100 | 10 秒 |
| HTTP 登录 | 1 / 10 / 50 / 100 | 10 秒 |
| TCP 连接+登录 | 10 / 50 / 100 | 串行建立 |
| 同节点消息 | 1 / 5 / 10 / 25 / 50 发送者 | 15 秒 |
| 跨节点消息 | 1 / 5 / 10 / 25 / 50 发送者 | 15 秒 |

消息测试中，每个发送者对应一个接收者，因此 50 个发送者实际维护 100 条 TCP 连接。

### 3.3 指标定义

| 指标 | 含义 |
| --- | --- |
| 成功率 | 成功响应数 / 总请求数 |
| 吞吐量 | 成功操作数 / 阶段实际持续时间 |
| ACK 延迟 | 发送方从发出 1017 到收到 1018 的时间 |
| 送达延迟 | 发送方从发出 1017 到接收方收到 1019 的时间 |
| p95 / p99 | 95% / 99% 请求不超过的延迟 |

每条测试消息使用唯一 ID，只有接收方收到相同 ID 的 1019 才计为送达成功。

### 3.4 测试数据创建

1. 通过测试 Redis 写入注册验证码。
2. 通过 Gate `/user_register` 创建 100 个用户。
3. 通过 HTTP 登录取得 Token。
4. 通过真实 TCP 协议创建 50 对好友关系。
5. 正式压测阶段复用这些账号与好友关系。

注册阶段使用并发 1。原因是并发 4 的冒烟数据创建中出现一次 `CALL reg_user` 返回 `-1`，随后被 Gate 映射为 1005。

## 5. HTTP 测试结果

### 5.1 注册

| 并发 | 成功数 | 吞吐 | p50 | p95 | p99 |
| --- | --- | --- | --- | --- | --- |
| 1 | 100/100 | 18.48 req/s | 50.2ms | 62.1ms | 73.1ms |

注册包含 Argon2id 密码哈希、Redis 验证码读取和 MySQL 存储过程调用。

| --- | --- | --- | --- | --- | --- |
| 1 | 2398.5 req/s | 0.37ms | 0.64ms | 0.79ms | 100% |

## 8. 结论

### 8.1 可以确认的能力

- 在该测试环境可以稳定维持 100 条已登录 TCP 连接。
- 同节点消息可达到约 1.1k msg/s。
- 跨节点消息可达到约 430 msg/s。
- 在本次负载规模内没有消息丢失或 ACK 失败。
- 断线后在线计数正确归零。

### 8.2 建议容量边界

以下边界以当前实验室数据和实际延迟目标为前提：

| 场景 | 建议 |
| --- | --- |
| HTTP 健康检查式请求 | 100 VUs 仍正常 |
| HTTP 登录 | 若要求 p95 小于 500ms，建议并发不超过约 10 |
| 同节点聊天 | 若要求 p95 小于 100ms，可运行到约 50 个持续发送者 |
| 跨节点聊天 | 若希望 p95 小于 150ms，建议控制在约 25 个持续发送者 |
| 同时在线连接 | 已验证 100 条；更大规模尚未验证 |

这些是“无思考时间”的压力上限，不代表正常聊天用户数。真实用户大多不会持续不间断发送消息。

## 9. 发现的问题

### 9.1 并发注册冲突

在冒烟数据准备中，两个不同用户并发注册时，一个成功，另一个收到 1005。Gate 将数据库返回的 `-1` 也映射成“用户已存在”，丢失了真实错误信息。

影响：

- 批量注册可能误报用户已存在。
- 前端难以区分真实重复账号和数据库并发错误。

建议：

- 数据库错误应映射为 `Database_Failed` 或单独错误码。
- 对 `reg_user` 的死锁/锁等待增加有限重试。
- 为并发注册增加自动化测试。

### 9.2 登录并发延迟

Argon2id 是安全设计的一部分，不适合为了压测吞吐而降低参数。应通过限流、排队和独立认证容量规划处理登录突发。

### 9.3 跨节点吞吐固定

跨节点吞吐约为同节点的 39%，且从 1 个发送者起就接近饱和。主要优化方向：

- 减少同步 gRPC 调用成本。
- 避免所有业务都经过单逻辑线程。
- 缓存或调整好友关系校验频率。
- 为跨节点转发建立更明确的队列和背压策略。

## 10. 测试限制

- 应用服务是 Windows Release；MySQL/Redis 是 Linux VM。该结果不能直接等同于 Linux 应用服务的性能。
- 所有组件运行在同一台物理主机，网络往返小于 1ms，不代表公网延迟。
- 压测器和应用服务共用 Windows CPU。
- SMTP、VerifyServer 邮件发送未参与测试。
- 每个聊天阶段持续 15 秒，只能判断短时容量，不能证明长时间无泄漏。
- 数据集仅 100 用户、50 对好友，未验证大表下的好友查询和列表加载。
- HTTP 健康检查每请求建立新连接，结果包含连接建立成本。
