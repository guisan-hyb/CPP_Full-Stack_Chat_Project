# 踩坑复盘：登录成功后客户端界面不跳转

> 复盘日期：2026-10-13

## 1. 排查方法论：先定位断点，再最小复现，最后反向锁定

### 1.0 三条总原则

1. **跨进程问题先怀疑"接口/协议字段"，再怀疑业务逻辑。**
   长度、字节序、字段名、端口这类"约定"最容易错，而它们出错时表现往往是"什么都没发生"，不像业务逻辑那样会抛异常或打日志。
2. **每个结论都要能被反向证伪。**
   "客户端没问题"不能靠读代码得来的自信，要能拿一个已知正确的对端去证明（第 3.2 节）。
3. **环境/配置类问题优先排除。**
   端口、编码、工作目录这三类问题会让"所有代码看起来都对"。其中端口问题用一张"谁监听 / 谁告知"对照表最快（第 2.2 节）。

### 1.1 第 0 步：把模糊现象改写成可观测命题

"没反应"是无法排查的，必须先翻译成"应该发生什么、实际观察到什么"：

| 用户的描述 | 排查前必须先确认的可观测量 |
| --- | --- |
| "登录成功后界面不跳转" | ① 界面有没有红字提示？② 登录按钮是否一直灰着？③ 客户端与 ChatServer 的 TCP 是否 ESTABLISHED？④ 服务端有没有打印那次登录？⑤ 客户端有没有收到 `ID=1006` 的包？ |

本次正是靠这张表把问题从"没反应"逼成了"**收包停在 `message_id: 1006 / message_len: 119` 之后**"——这就只剩一种可能：包体没凑齐。

### 1.2 第 1 步：沿链路切段，找"最靠前的断点"

登录跳转这条链路一共 6 段，逐段确认"这一段过了没有"，而不是通读代码：

```mermaid
flowchart LR
    A["点击登录"] --> B["HTTP /user_login<br/>GateServer"]
    B --> C["StatusServer 分配<br/>host/port/token"]
    C --> D["TCP 连接 ChatServer<br/>（长连接）"]
    D --> E["发 1005 ID_CHAT_LOGIN"]
    E --> F["收 1006 ID_CHAT_LOGIN_RSP"]
    F --> G["emit sig_switch_chatDlg<br/>切聊天界面"]
    style D fill:#ffe6e6
    style F fill:#ffe6e6
```

本次排查在这条链上确认真实断过两次：**第一次断在 D（端口不匹配）**，修好之后**断在 F（回包不完整）**。

### 1.3 第 2 步：用最小复现绕开不可信的组件

怀疑"客户端解析有问题"时，不要盯着 Qt 源码猜，直接把客户端**替掉**：

- 用 gRPC 调 StatusServer 的 `GetChatServer` 拿一个合法 token；
- 用 Node 的 `net` 按客户端完全相同的格式（`[id 2B][len 2B 大端][JSON]`）发登录包；
- 看服务端到底回不回、回什么字节。

这一步的价值：把"Qt 客户端 / ChatServer / Redis+MySQL"三者解耦，**先确认服务端到底有没有问题**。

### 1.4 第 3 步：造一个"已知正确"的对端做反向验证

确认服务端"会回包"之后，要回答的是"回的包对不对"。做法是把客户端的 `readyRead` 代码**原样抽出来**编成一个小探针（Qt 6.11 真机环境），分别对着两个对端跑：

- 对着**真实 ChatServer** → 卡住；
- 对着**我自己写的、组帧正确的假服务端** → 一次通过。

并且探针特意做了两组对照（`mode 1` 用客户端原代码，`mode 2` 用手写大端解析）——**两组结果一样**，于是可以排除"`QDataStream` / Qt 版本"这类诱因，把怀疑对象收敛到"帧本身"。

### 1.5 第 4 步：用守恒量对账，落到具体一行

到了这一步，手里已经是一堆数字，关键动作是**算差值并解释差值的含义**：

| 观测 | 数字 | 差值 |
| --- | --- | --- |
| 服务端抓到的原始帧 | 头部声明 91，实收包体 87 | **4** |
| 用户提供的客户端日志 | `message_len: 119`，uid=8 真实包体 115 | **4** |

差值恒为 4，且 4 正好等于 `HEAD_TOTAL_LEN`（包头长度）——直接指向"写头部的那个地方用了总长度"这一行代码，而不是"偶发"。

> 经验：**差值往往比绝对值更有信息量**。看到 4、8、2 这种"和结构尺寸相同"的差值，先怀疑头部/长度字段。

## 2. 本次案例：完整因果链与证据

### 2.1 现象

给服务端做了分布式改造（StatusServer 按负载分配 + ChatServer 作为独立 gRPC/长连接服务）后，客户端登录**看起来成功**，但界面停在登录页不跳转，且**没有任何错误提示**。

### 2.2 第一层：配置层——"谁监听"和"谁告知"对不上

登录时序里，客户端要连的地址是 **服务端告诉它的**：

```
GateServer /user_login → StatusGrpcClient → StatusServer::GetChatServer
        ↓ 读 [chatservers][chatserverN]Host/Port
返回 { host, port, token } → 客户端 TcpMgr::slot_tcp_connect
```

而 ChatServer 改造后改成用 `[SelfServer]Port` 决定监听端口：

| 角色 | 配置键 | 值 |
| --- | --- | --- |
| ChatServer 实际监听 | `[SelfServer]Port` | 8090（ChatServer2：8091） |
| StatusServer 登记给客户端 | `[chatserverN]Port` | 8990 / 8991 |

**实测**（启动 ChatServer 后直接探测端口）：

```
Redis connect success
RPC Server listening on: 0.0.0.0:50055
Server start success, on port: 8090

port 8090 : CONNECTED
port 8990 : FAILED -> 由于目标计算机积极拒绝，无法连接
port 8991 : FAILED -> 由于目标计算机积极拒绝，无法连接
```

→ 客户端连 8990 直接被拒绝，链路断在第 1.2 节的 D 段。

**修复**：统一端口。`[SelfServer]Port` 改成 8990/8991（与登记值一致），并把两个聊天服务器之间的 gRPC 地址改用 `RPCPort`（50055/50056），避免和长连接端口混用。

### 2.3 第二层：客户端的"静默失败"（问题放大器）

改完端口后仍不跳转，而且**什么都不显示**。原因在客户端本身：

```cpp
// client/tcpmgr.cpp —— 修改前
QObject::connect(&_socket, ..., [&](QAbstractSocket::SocketError socketError) {
    Q_UNUSED(socketError)
    qDebug() << "Error:" << _socket.errorString();   // 只打日志，不发信号
});
```

没有失败信号、也没有超时 → `LoginDialog` 的 `slot_tcp_conn_finish(false)`（"网络异常"+ 恢复按钮）永远不会执行，按钮就那样灰着。**任何服务端故障都会被伪装成"没反应"**。这一层虽然不制造故障，但让第一个故障极难被发现。

### 2.4 第三层：真正的根因——帧长度字段多了 4 字节

修好端口后，服务端日志显示登录处理**完整跑完**（连 `GetBaseInfo` 的用户信息都打印了），客户端日志却停在这里：

```
Connected to server!
message_id:  1006   message_len:  119        ← 解析出了包头，然后就没有然后了
```

而客户端的收包逻辑是：

```cpp
QDataStream s(&_buffer, QIODevice::ReadOnly);
s >> _message_id >> _message_len;      // 这个字段被当作“包体长度”
_buffer.remove(0, 4);
if (_buffer.size() < _message_len) {   // 包体不够 → 等下一次 readyRead
    _b_recv_pending = true;
    return;
}
```

客户端手上只有 115 字节包体，头部却说 119 → **它一直在等那 4 个字节，而服务端已经发完了**，所以永远等不到，`handleMsg` 从不执行，`sig_switch_chatDlg` 从不发出。

根因在服务端 [MsgNode.cpp](C:/Users/Mycode/C++_Full-Stack_Chat_Project/server/ChatServer/MsgNode.cpp:27)（ChatServer2 是同一份拷贝）：

```cpp
SendNode::SendNode(const char* msg, short max_len, short msg_id)
    : MsgNode(max_len + HEAD_TOTAL_LEN), _msg_id(msg_id)   // 缓冲区大小 = 包体 + 4，这是对的
{
    ...
    // ❌ 错误：写进头部的是 _total_len（包头 + 包体）
    short len_to_net = net::detail::socket_ops::host_to_network_short(_total_len);
    // ✅ 正确：头部这个字段的语义是“包体长度”
    // short len_to_net = net::detail::socket_ops::host_to_network_short(max_len);
```

**帧结构对照**：

| 字段 | 长度 | 本次值 | 写入方 | 读取方 | 语义 |
| --- | --- | --- | --- | --- | --- |
| `msg_id` | 2B 大端 | `0x03EE` = 1006 | `SendNode` | 客户端 `TcpMgr` | 消息 ID |
| `len` | 2B 大端 | `0x0073` = 115（错时写成 119） | `SendNode` | 客户端 `TcpMgr` | **包体字节数** |
| `body` | `len` | JSON 文本 | `SendNode` | 客户端 `TcpMgr` | 消息内容 |

```
正确（len = 包体长度）
  03 EE | 00 73 | <115 字节 JSON>          共 4+115 = 119 字节
  客户端：读到 115 == 声明 115 → 处理 ✅

本次（len = 包头+包体）
  03 EE | 00 77 | <115 字节 JSON>          共 4+115 = 119 字节
  客户端：读到 115 < 声明 119 → 永远等 4 个字节 ❌
```

### 2.5 为什么以前一直没暴露

同一套"这个字段 = 包体长度"的约定，在另外三个地方都是对的，只有服务端的发送方向写错了：

| 位置 | 方向 | 长度字段怎么算 | 状态 |
| --- | --- | --- | --- |
| `client/tcpmgr.cpp` `slot_send_data` | 客户端 → 服务端 | `quint16(dataBytes.size())` | ✅ |
| `server/CSession::HandleReadHead` | 读客户端包 | 按包体长度读 `RecvNode(msg_len)` | ✅ |
| `server/SendNode` | 服务端 → 客户端 | 用了 `_total_len`（+4） | ❌ |
| `client/TcpMgr` `readyRead` | 读服务端包 | 按包体长度等 | ✅ |

而"服务端 → 客户端"这个方向，在登录回包之前**从来没有发过任何消息**（搜索回包、好友申请通知、聊天消息都还没做），所以这个 bug 一直没被触发。

> 结论：这不是"登录功能"的 bug，而是**所有服务端推送**的 bug——只要那条线不改，后面每加一个推送功能都会以"客户端没反应"告终。

## 3. 验证工具箱（本次用到的 5 类手段）

### 3.1 裸协议发包：用脚本替掉客户端

```javascript
// 1) 用 gRPC 调 StatusServer 拿 token（等价于 GateServer 做的事）
const rsp = await statusClient.getChatServer({ uid });      // { host, port, token }

// 2) 按客户端完全相同的帧格式发登录请求
const body = Buffer.from(JSON.stringify({ uid, token }), "utf8");
const head = Buffer.alloc(4);
head.writeUInt16BE(1005, 0);        // ID_CHAT_LOGIN
head.writeUInt16BE(body.length, 2);
sock.write(Buffer.concat([head, body]));
```

要点：**读数时要严格校验"实收字节数 == 4 + 声明长度"**，并把"是否匹配"显式打印出来（见第 6 章踩坑 1）。

### 3.2 假对端：证明"客户端代码本身没问题"

写一个只做一件事的假服务端——按正确语义组帧：

```javascript
const body = Buffer.from(JSON.stringify({ error: 0, uid: 8, name: "test5", ... }), "utf8");
head.writeUInt16BE(1006, 0);
head.writeUInt16BE(body.length, 2);   // 注意：这里写的是“包体长度”
sock.write(Buffer.concat([head, body]));
```

让同一份客户端代码分别对"真服务端"和"假服务端"，结论立刻清晰：**一边卡死、一边通过 → 问题在帧，不在客户端**。

### 3.3 把可疑代码片段抽出来单独跑

把 `readyRead` 那段代码原样复制到一个小 Qt 控制台程序里，并给出两种模式做对照（原写法 / 手写大端解析）。好处：

- 不用整机跑客户端，几秒就能得到一个可复现的结论；
- 对照实验能排除"是不是 Qt 版本/某个 API 的锅"。

### 3.4 编码敏感文件的修改与验证

- 服务端这几份源码是 **GBK** 编码，直接用 UTF-8 工具整文件重写会把中文注释变成乱码。做法是：**按 936 读、按 936 写**，改完做字节级比对，确认"除被替换的函数外完全一致"（本次比对结果：前缀 4700 字节完全相同）。
- **【2026-10-14 更新】本节这条约定已经失效，以上只作为当时的历史记录保留。** 服务端 44 个 GBK 文件已统一转为 UTF-8（无 BOM），此后**按 UTF-8 读写即可，不再需要 936 往返 + 字节比对**；`/utf-8` 编译选项从此与源码真正一致，MSVC 的 `C4828` 警告（当时每次全量编译约 3000 条）也归零了。转换过程、四层校验与踩过的坑见《复盘-服务端源码编码统一为UTF8.md》。
- 本机沙箱里 MSBuild 因 Windows SDK 路径被拦，改用 `g++ -fsyntax-only` + 真实头文件（nlohmann / gRPC / redis++ / Boost / mysqlx）做**语法与类型**验证；客户端则用它自己的 qmake Makefile 真编真链。

### 3.5 端口与连接状态探测（环境受限时的替代手段）

- `Get-NetTCPConnection -State Listen` 在该环境返回空 → 不要据此下"没人监听"的结论，改用：
  - `netstat -ano | findstr :8990`：看 LISTENING / ESTABLISHED 和 PID；
  - 直接 `TcpClient` 连接探测：`8090 CONNECTED` / `8990 拒绝` 是最直观的证据。

## 6. 复盘：我这次排查踩的坑

1. **探针脚本"看起来正常"，其实是它在骗我。**
   第一版 Node 探针用 `buf.slice(4, 4 + declared)` 取包体，越界时 JS 会**静默截断**，正好打印出一份完整 JSON，于是我得出"服务端回包正常"的错误结论，把方向带偏了一整轮。
   教训：探针必须显式校验 `实收 == 4 + 声明`，并且把"是否匹配"打印出来；**取数据的代码越界钳位是排查中的隐形陷阱**。
2. **把"后来的探针全超时"当成了"服务端卡死"。**
   我据此写了一整套"工作线程阻塞"的解释，还顺势挖出了几个真实但非主因的缺陷。事后看，那次超时里混入了我自己探针造成的干扰（例如用不存在的 uid 走 MySQL 分支）。
   教训：**探针自己会改状态**，观测前先想清楚"这次观测会不会污染下一次观测"；同一个现象要用两条独立路径交叉验证，不能只靠一条。
3. **`Get-NetTCPConnection` 返回空，我差点当成"服务没监听"。**
   工具返回空 ≠ 事实为空。换 `netstat -ano` 和 `TcpClient` 直连立即确认。
4. **改编码敏感文件差点把中文注释写坏。**
   GBK 源文件用 UTF-8 工具整写会乱码。后来按 936 读写 + 字节级比对，把风险收敛掉了。
5. **"客户端不出错"本身就是关键线索。**
   一个只 `qDebug`、既不上报失败也不设超时的接收方，会把任何故障伪装成"没反应"——这也是我把客户端加固列为必做项的原因。

## 附录 B：协议与常量速查

| 名称 | 值 | 说明 |
| --- | --- | --- |
| `HEAD_ID_LEN` / `HEAD_DATA_LEN` / `HEAD_TOTAL_LEN` | 2 / 2 / 4 | 大端 |
| `ID_CHAT_LOGIN` / `ID_CHAT_LOGIN_RSP` | 1005 / 1006 | 客户端与 ChatServer 必须一致 |
| `MSG_CHAT_LOGIN_RSP` | 1006 | 服务端侧同名常量 |
| `MAX_LENGTH` | 2048 | 服务端对 `msg_id` / `msg_len` 的合法性上限 |
| `USERTOKENPREFIX` | `utoken_` | StatusServer 写入、ChatServer 校验，两边必须同前缀 |
| `USER_BASE_INFO` | `ubaseinfo_` | 用户信息缓存 key |
| `LOGIN_COUNT` | `logincount` | 各聊天服务器在 Redis Hash 里的在线计数（负载均衡用） |

**排查一句话口诀**：先确认链路断在哪一段 → 再用最小复现替掉可疑组件 → 再造一个正确对端反向验证 → 最后用差值对账落到那一行。
